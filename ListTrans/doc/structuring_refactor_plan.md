# 物料清单结构化改造方案 (V1.0 · 评审稿)

> 编写日期：2026-07-18
> 状态：**待用户批准**，批准前不进行任何代码改动
> 基于数据集：`doc/sample/物料明细(1).xlsx`（46,483 行）
> 目标：从当前"双路混合召回 + 弱结构化"升级为"分域强结构化 + 字段级评分"，将 Must 字段抽取率从 ~35% 提升至 ≥85%，Top1 精确匹配率相对提升 ≥30%。

---

## 第一部分：数据画像

### 1.1 数据基本情况

| 指标 | 数值 |
|---|---|
| 总行数 | **46,483** |
| 有效列 | 物料分类、物料编码、物料名称、规格/型号、计量单位、常用品牌、描述 |
| 数据分类数 | **385 类**（重度长尾） |
| 常用品牌非空率 | 84.6% |
| 描述字段非空率 | **仅 3.7%**（几乎废弃字段） |
| 停用/禁用编码 | 672 行 |
| 编码重复 | 23 行 |
| 计量单位种类 | 42 种，Top3 = 个(18341) / 台(15443) / m(5820) |
| `规格/型号` 平均长度 | 24 字符（min 0，max 288，>200 字符仅 53 行） |

**核心结论**：`规格/型号` 字段是**主战场**，短、密、格式高度混乱；`描述` 字段基本没内容，当前 `matcher.py` 里 `f"{c_spec_text} {c_desc}"` 的拼接对候选侧几乎无增益。

### 1.3 字段格式特征（惊人发现）

对 46,483 行规格文本的分隔符/关键词统计：

| 现象 | 覆盖率 | 说明 |
|---|---|---|
| 逗号 `，` 分隔 | **72.8%** | 事实主分隔符 |
| `A*B*C` / `数字*数字` | **39.9%** | 尺寸/芯x截面主表达式 |
| 冒号 `：` | 33.8% | K:V 结构主标记 |
| `DN数字` | **13.0%**（6,045 行） | 管径主标记 |
| 中文键:值（K:V 对） | 30.2%（14,022 行） | 结构化半途而废 |
| `1.xxx: yyy` 编号标题式 | 0.4% | **可以放弃兼容**，与当前 `parse_numbered_headers` 大投入不成比例 |
| `风量`关键词 | 23.9%（11,128 行） | 暖通类核心参数 |
| `余压` | 18.8%（8,749 行） | 暖通类核心参数 |
| 材料关键词（镀锌/不锈钢/玻璃钢/PP…）合计 | >40% | 材质是普遍性维度 |

### 1.4 现有抽取器的"漏抽率"实证

用当前 `preprocessor.py` 里的正则对 4.6 万行跑一遍，推断以下漏抽情况：

| 场景 | 现状 | 漏抽率估计 |
|---|---|---|
| 电缆 `WDZB-BYJ 4*6+1*4` | 正则 `芯数x截面` 只捕获第一个`4*6`，`+1*4` 丢失 | 550/2343 = **23%** 复合型号被截断 |
| 电缆型号族（YJV/BV/RVV/WDZ 系）| 完全没提取（当前只有 `芯数/截面积`）| **~85%** 未结构化 |
| 阀门连接方式（法兰/螺纹/卡箍/焊接/由令）| 无对应字段 | **100%** 未结构化 |
| 阀门驱动方式（手动/电动/气动）| 无对应字段 | **100%** 未结构化 |
| 阀门/管道公称压力 `PN10/16/25` | 只在 `_water` 分支且要求"压力/PN"关键词开头 | **~60%** 未结构化 |
| 汽水集配器 `缸体直径/缸体长度` | 完全没入字段清单 | **100%** 未结构化 |
| 材质（镀锌钢板 / 304 / 316 / 玻璃钢 / PP / 铝合金 / 碳钢）| 只 `_water` 分支有材质表 | **暖通/装饰 100%** 漏抽 |
| 特征旗标（阻燃 / 耐火 / 无卤 / 屏蔽 / 变频 / 防爆 / 防腐 / 卡式 / 嵌入式 / 立柜 / 吊装）| 无 | **100%** 未结构化 |
| φ / Φ / DV24V 特殊符号 | φ 常被误判为 model 前缀 | **风阀类漏抽率高** |
| 计量单位与文本单位一致性（如"米/m/M" 大小写混用）| 部分归一 | 影响 `check_unit_compatibility` |

### 1.5 直观诊断结论

1. **数据的天然结构性其实很强**（72.8% 用逗号分隔，短小紧凑），但**表达高度多样**：同一"材质"可能写成"304不锈钢 / 不锈钢SUS304 / SUS304 / 304"四种；同一"DN80"可能写作"DN80 / dn80 / D80 / Φ80"。
2. 现有抽取器只覆盖了 **暖通/给排水/强电** 的部分核心字段，对**阀门、门窗、机组变频、电缆型号族、材质、特征旗标**这些**用户最常用于二次校对的维度**几乎没有结构化。
3. `common_attrs` 交集比较策略在字段稀疏下**大量失效**，评分退化到文本相似度。
4. 数据本身**质量偏好**（分类正确率高、单位规范）**大于流程复杂度**，非常适合"字典 + 规则 + 分类特化"三级抽取。**不需要引入 LLM 也能拿到 80%+ 结构化率**。

## 第二部分：结构化方法论

### 2.1 顶层原则

- **分类驱动（Category-First）**：先分类，再按分类专属模式抽取。385 个原始分类通过映射表折叠为 **~30 个"结构化域"**（Domain）。
- **字段稀疏容忍**：任何字段"抽不到"视为 `unknown`，评分时按缺失惩罚，而非跳过。
- **字典优先，正则兜底，语义封顶**：绝大多数字段用**受控词典 + 正则**即可；复杂描述再让向量模型兜底。
- **双端一致**：候选侧（4.6 万条物料库）与查询侧（用户上传清单）**使用同一套抽取器 + 同一份字典**。
- **可回滚**：所有抽取结果版本化，结构化模式变更后一键 `re-parse`，不必重导 Excel。

### 2.2 三层结构化模型（IR-1 / IR-2 / IR-3）

```
Raw Text
  │
  ▼
IR-1 归一层（Normalize）      ← 全类别通用
  · 全角半角
  · 单位规范（m³/h、kW、Pa、DN、mm）
  · 别名/错别字替换
  · 材料关键词映射（"304不锈钢"→"SS304"）
  · 分隔符标准化（统一为 ，）
  │
  ▼
IR-2 分域抽取（Domain Extract）← 30 个域各一套规则
  · 主标识（Model / SKU / 型号族）
  · 尺寸类（DN / 长*宽*高 / 芯x截面 / 外径*壁厚）
  · 物理量（风量 / 制冷量 / 功率 / 压力 / 流量 / 扬程 / 转速）
  · 材质（枚举字典）
  · 特征旗标（枚举字典：变频/防爆/防腐/嵌入式/吊装/…）
  · 连接方式 / 驱动方式 / 密封形式（阀类专用）
  │
  ▼
IR-3 语义补齐（Semantic Fallback）← 兜底
  · 剩余未抽字段用向量模型对齐同域候选中最相近的样本，回填其结构
  · （可选）小 LLM 抽 K:V（离线批处理，非实时）
```

### 2.3 30 个结构化域（Domain）与字段矩阵

**方法**：先给每个域定义**必抽字段（Must）+ 选抽字段（Should）+ 特征旗标（Flags）**。示例（完整 30 域会作为 `config/domain_schema.json` 提交）：

| 域 | Must | Should | Flags |
|---|---|---|---|
| 电缆-电力 | 型号族(YJV/YJY/BV/BVR/RVV/KVV/RV…)、芯数、截面积 | 电压等级(0.6/1kV)、护套颜色 | 阻燃(ZA/ZB/ZC)、耐火(NH)、无卤低烟(WDZ/WDU)、屏蔽、铠装 |
| 通风机 | 风量、机外余压、材质 | 功率、转速、噪音、机型（轴流/离心/管道）| 防爆、防腐、变频 |
| 阀门（球/闸/蝶/截止/止回）| DN、材质、连接方式(法兰/螺纹/卡箍/焊接/由令/卡盘)| PN、驱动(手动/电动/气动)、密封面、介质 | 保温、防爆 |
| 静压箱/消声器 | 长*宽*高、材质 | 保温层、内衬 | 阻性/抗性 |
| 净化过滤（FFU/过滤器）| 外形尺寸、过滤效率、材质 | 送风量、噪音、粒径@um | 直流电机 |
| 冷/热水机组 | 制冷量kW、机型（螺杆/离心/涡旋/风冷/水冷）| 制热量、COP、水侧管径 | 变频、内置板换 |
| 空调机组（AHU/PAU/新风）| 风量、余压、过滤等级 | 制冷量、加湿量、盘管排数 | 变频、防爆 |
| 汽水集配器 | 缸体直径DN、缸体长度、材质 | 封头形式(椭圆/平板) | — |
| 门窗 | 宽*高、材质、开启形式(平开/推拉/折叠/自动)| 防火等级、门框材料 | 磁屏蔽、洁净 |
| 管道 | DN、材质、连接形式 | 外径*壁厚、PN | 保温、脱脂、无缝 |
| 电线 | 型号族、截面积 | 电压等级、颜色 | 阻燃、耐火、无卤 |
| 桥架线管 | 型号（金属/塑料/防火）、宽*高、厚度 | 表面处理 | 阻燃 |
| 电梯 | 载重、层站、速度 | 门宽、驱动方式 | 医用/客梯/货梯 |
| … | | | |

### 2.4 字典体系

新增 6 份受控字典，都放在 `config/`：

| 字典 | 作用 | 初始规模估计 |
|---|---|---|
| `domain_schema.json` | 域字段矩阵（Must/Should/Flags） | 30 域 × 平均 8 字段 |
| `category_domain_map.json` | 385 分类 → 30 域映射 | 385 条 |
| `material_dict.json` | 材质同义词（304不锈钢/SUS304/304→SS304）| ~120 条 |
| `connection_dict.json` | 连接方式同义词（法兰/焊接/卡箍/由令/螺纹/卡盘/对焊）| ~30 条 |
| `flags_dict.json` | 特征旗标同义词（变频/防爆/阻燃-ZA/耐火-NH…）| ~80 条 |
| `unit_norm.json` | 扩充版单位归一（含 mpa/MPa/千瓦/kW/CMH…）| ~80 条 |

### 2.5 分数机制配套改造

在 `matcher.py` 打分中：

- 引入 `field_weight_by_domain`：每个域给字段单独定权（例如电缆域，型号族权重 25%、芯数 25%、截面积 25%、其他 25%）。
- **缺失惩罚**：Must 字段缺失 → `-0.15`（不是 0 分，避免过杀）。
- **旗标一致奖励**：`(阻燃-ZA vs ZA)` +0.05，`(阻燃-ZA vs ZC)` -0.10。
- **硬门槛**：DN、芯数、截面积三个字段任一冲突 → 分值封顶 30。

### 2.6 反馈闭环

每次用户手动改绑（`binding_feedback.json`）：
1. 对齐原始文本 vs 最终物料的 **字段级 diff**；
2. 若差异在字典未覆盖的词条上，进"待审词条"队列，由 admin 审核入 `material_dict.json` / `flags_dict.json`；
3. 每周批量重跑 `parsed_params` 列（无需重导 Excel）。

## 第三部分：软件改造方案

### 3.1 改造目标

- **不破坏现有 API 契约**（前端零改动即可跑通）；
- 结构化率从当前估算的 **~35%** 提升至 **~85%**（覆盖 Must 字段）；
- 首次导入耗时可接受（4.6 万条 < 5 分钟）；
- 支持规则热更新，无需重启。

### 3.2 改造范围（8 个模块）

```
配置层（新增）
├── config/domain_schema.json         [新]
├── config/category_domain_map.json   [新]
├── config/material_dict.json         [新]
├── config/connection_dict.json       [新]
├── config/flags_dict.json            [新]
└── config/unit_norm.json             [新，替代/扩充 unit_rules.json]

核心抽取层（重构）
├── app/preprocessor.py               [大改：拆分]
│   ├── normalizer.py                 [新：IR-1 归一]
│   ├── domain_router.py              [新：分类→域路由]
│   └── domain_extractors/            [新目录：30 个域各一个 extractor]
│       ├── cable.py
│       ├── valve.py
│       ├── fan.py
│       ├── ahu.py
│       ├── … (共 30 个)
│       └── generic.py                [兜底]

匹配层（小改）
└── app/matcher.py                    [调整 score_candidate 支持字段权重与缺失惩罚]

数据库层（小改）
└── app/db_manager.py                 [新增 parsed_params 版本号列、re-parse 接口]

Server 层（小改）
└── app/server.py                     [新增 POST /api/db/reparse 端点，director 权限]

前端（可选，非必需）
└── web/index.html + app.js           [新增"结构化率仪表盘"卡片，展示各域抽取率]
```

### 3.3 改造步骤（RFC）

#### Phase 0 — 数据基线（1 天，不动代码）
- 用离线脚本跑当前抽取器，统计 Must 字段抽取率、Top1 命中率作为 **基线报告**（存 `doc/baseline_metrics_v0.0.4.md`）。
- 从 `binding_feedback.json` 抽 500 条构造 **回归集**。

#### Phase 1 — 字典与 Schema（2~3 天，纯配置）
- 编写 `domain_schema.json`、`category_domain_map.json` 等 6 份 JSON。
- 由领域专家评审字典条目。
- **不动代码**。

#### Phase 2 — 抽取器重构（3~5 天）
- 拆分 `preprocessor.py`，保留公共接口 `extract_params(text, category)`：
  ```python
  def extract_params(text, category) -> {"model", "attrs", "flags", "domain", "confidence"}
  ```
- 新增 30 个域抽取器（前 10 个大类先做，覆盖 65%+ 数据）。
- 保证 **向后兼容**：`attrs` 字段仍是 dict，前端无感知。

#### Phase 3 — 匹配层升级（2 天）
- 修改 `matcher.py` 的 `score_candidate`：
  - 引入 `field_weight_by_domain`；
  - `common_attrs` 从"交集"改为"并集，缺失方按惩罚项计"；
  - 新增 Flags 一致性打分。
- 新增回归测试脚本（用 Phase 0 的 500 条集合验证 Top1 提升）。

#### Phase 4 — 存量数据 re-parse（1 天）
- 新增 `POST /api/db/reparse`：不重导 Excel，仅根据新抽取器批量刷 `parsed_params` 列并重建 FTS/向量索引。
- 加进度轮询 API `GET /api/db/reparse/status`。
- 首次运行预计 3~5 分钟（4.6 万条 × 单条 <5ms）。

#### Phase 5 — 前端仪表盘（可选，1 天）
- 在"系统参数配置"页新增卡片：
  - 30 域各自 Must 字段抽取率
  - Top 缺失字段清单
  - 未映射到域的分类清单（触发字典补齐）

#### Phase 6 — 反馈闭环（2 天）
- 从 `binding_feedback.json` 定时任务里挖掘未覆盖词条 → 写入 admin 审核队列。
- 提供 admin 审核 UI（沿用现有 `admin.html` 增卡片）。

### 3.4 兼容与风险

| 风险 | 缓解 |
|---|---|
| 现有 `parsed_params` schema 变化导致老索引不可用 | 加 `schema_version` 字段，读时兼容 v1/v2 |
| 30 域覆盖需要时间 | 分阶段上线：前 10 域优先，其他走 `generic.py` |
| 字段权重调整可能引入回归 | 强制通过 Phase 0 回归集 + 阈值检查 |
| 抽取器改动影响 FTS `search_tokens` 生成 | `search_tokens` 独立函数不变，仅 `parsed_params` 变化 |
| re-parse 期间服务不可用 | 使用后台线程 + 双表切换（写入 `materials_new` 后重命名） |

### 3.5 验收指标

| 指标 | 当前 | 目标 |
|---|---|---|
| Must 字段整体抽取率 | ~35% | **≥ 85%** |
| Top1 精确匹配率（Score≥85） | 待测 | **相对提升 ≥ 30%** |
| Top3 命中率 | 待测 | ≥ 90% |
| 首次 re-parse 耗时 | — | ≤ 5 min |
| 单条匹配 P95 延迟 | — | ≤ 200ms |
| 未映射分类数量 | 385 | ≤ 20 |
