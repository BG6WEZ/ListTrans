## 二、报告未提及的关键稳定性隐患（新见解）

### 🚨 H1. `hybrid_recall` 每行都开一次 SQLite 连接——报告只修了 `query_by_code`，忘了大头

[matcher.py#L861-L866](file:///c:/Users/wangd/project/ListTrans/ListTrans/app/matcher.py#L861-L866) 在 `hybrid_recall` 中：
- 通道 A1：`get_db_connection()` + `LIKE` 查询
- 通道 A2：`search_materials_keyword`（内部再开连接）
- 通道 A2 中文子查询：`search_materials_keyword`（再开连接）

**1000 行清单 → 至少 3000 次 SQLite 连接开合**，才是真正的 IO 风暴。`query_by_code` 的 lru_cache 只能覆盖极少数场景。

**建议**：在 `db_manager` 加单进程连接池（thread-local `sqlite3.connect(check_same_thread=False)`）+ WAL 模式，或预加载 45k 物料到内存 dict。

### 🚨 H2. `ThreadPoolExecutor(max_workers=10)` + SentenceTransformer 的 GIL 竞争

[server.py#L436](file:///c:/Users/wangd/project/ListTrans/ListTrans/app/server.py#L436) + [server.py#L755](file:///c:/Users/wangd/project/ListTrans/ListTrans/app/server.py#L755)：
- 10 个线程并发跑 `match_item`，每个内部再触发 SQLite 查询；
- 批量 encode 在主线程完成 ✅，但 `match_item` 内部 fallback 分支（[matcher.py#L908](file:///c:/Users/wangd/project/ListTrans/ListTrans/app/matcher.py#L908)）仍会触发 `encode_single_query`，与主线程争 `self._lock`；
- 多线程 SQLite 写操作可能触发 `SQLITE_BUSY`。

**建议**：`max_workers` 降到 **4**，禁用 fallback encode，模型访问严格串行。

### 🚨 H3. 冷启动模型下载路径——内网死锁

[vector_index.py#L52-L55](file:///c:/Users/wangd/project/ListTrans/ListTrans/app/vector_index.py#L52-L55)：
```python
print(f"Offline model not found at {offline_model_path}. Loading/downloading model from HF Hub...")
self.model = SentenceTransformer(model_path)
```
若 [model_offline/](file:///c:/Users/wangd/project/ListTrans/ListTrans/model_offline) 缺失，会尝试联网下载，内网环境完全卡死。

**建议**：
1. 强制 `HF_HUB_OFFLINE=1`；
2. 模型缺失时立即抛错，前端友好提示；
3. `_initialize_model` 加 `timeout=10s` 兜底。

### 🚨 H4. 前端 `showLoading` 无全局 Timeout——报告点名了却没实现

[web/app.js#L691-L699](file:///c:/Users/wangd/project/ListTrans/ListTrans/web/app.js#L691-L699) 仅为 `.style.display='flex'`，报告作为"解决方案"提出的 30s 兜底**未在代码中落地**。

**建议**：立即注入全局 SafetyTimer。

### 🚨 H5. 后端 `/api/upload` 无超时护栏 & 无进度反馈

- FastAPI 默认无请求超时，长清单一旦卡在一个 chunk，客户端只能无限等待；
- 反代（Nginx）通常 60s 超时，但 uvicorn 直挂时前端可能收到 502 或纯 hang。

**建议**：`upload_file` 内包一层 `asyncio.wait_for(..., timeout=90)`，或改为任务 ID + 轮询/SSE 进度。

### 🚨 H6. `batch_match_rows` 是双轮匹配——报告没提的隐藏耗时

[server.py#L816-L818](file:///c:/Users/wangd/project/ListTrans/ListTrans/app/server.py#L816-L818)：
```python
if not res["is_exact"] and confirmed_series:
    res = match_item(q_info, q_vector, confirmed_series)
```
一旦第一轮有若干精准命中，非精准项几乎全部会被 rerun 一次，耗时翻倍，报告耗时表明显低估了。

### 🚨 H7. `logging` 与 `print(DEBUG:...)` 混用

[server.py#L697/#L708/#L727/#L733/#L751](file:///c:/Users/wangd/project/ListTrans/ListTrans/app/server.py#L697) 大量 `print("DEBUG:...")`，生产环境会污染 stdout，且被 uvicorn 缓冲阻塞时也可能拖慢。

**建议**：全部改用 `logger.debug()`，通过环境变量控制级别。

### 🚨 H8. `admin_api` 中模型热重建接口缺少保护

[app.js#L2173](file:///c:/Users/wangd/project/ListTrans/ListTrans/web/app.js#L2173) 有"导入物料库并重建 FAISS 向量索引"入口——如果误触，会占用 CPU 数分钟，前端只有 loading 遮罩无进度条，用户极易误判死锁。

**建议**：这类操作必须走异步任务 + 进度轮询，并加权限确认弹窗。

## 三、耗时预估表 · 独立复评

**关键常数**（MiniLM-L12-v2 384d 纯 CPU）：
- 单批 encode 吞吐 ≈ 100~150 行/秒（batch_size=64）
- 45k×384 numpy 点积 + argpartition ≈ 10~15 ms/query
- 每行 SQLite（3 次连接 + FTS5 + 100 行结果）≈ 8~15 ms
- `score_candidate` 遍历 ~1000 候选 ≈ 5~10 ms/query
- 双轮匹配（H6）放大系数约 1.5~1.8×

| 规模 | Coding AI 预估 | 独立复评 | 差异 |
| :---: | :---: | :---: | :---: |
| 100 行 | 0.8~1.5 秒 | **1.5~3.0 秒** | 偏乐观 ~2× |
| 300 行 | 2.0~3.5 秒 | **4.0~7.0 秒** | 偏乐观 ~2× |
| 500 行 | 3.5~5.0 秒 | **7.0~12 秒** | 偏乐观 ~2× |
| 1000 行 | 7~10 秒 | **15~25 秒** | 偏乐观 ~2.5× |

**建议优化目标（结合 H1~H6 修复后）**：
- 100 行 ≤ 3 秒（可达）
- 300 行 ≤ 7 秒（可达）
- 500 行 ≤ 12 秒（需 H1+H6 优化）
- 1000 行 ≤ 25 秒（需 H1+H2+H6 全面优化）

## 五、对本项目的建议

1. **停止一切功能开发**，专注于 P0 三项修补（H4+H3+H5），累计约 30 行代码，可立竿见影解决"永久转圈"和"看起来卡死"的用户观感。
