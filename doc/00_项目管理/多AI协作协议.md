# 多 AI 轮流工作协议（1.0）

生效日期：2026-11-12。角色由用户指定；当前聊天为统筹 AI。适用于 V0.1.5～V0.2.0。用户指令优先；协议修改必须由统筹记录原因、影响和新修订号。

## 1. 工作单元与权责

每个版本拆成可独立复核的任务包，例如 `V015-M0`。同一任务包可以多轮整改，轮次用 `R01`、`R02`，不会因返工重复创建版本。

| 角色 | 可以做 | 不可自行做 |
|---|---|---|
| 统筹 AI | 下发任务包、变更裁决、维护进度、抽查证据、终审、批准下一版本 | 无证据宣称通过；代替用户授予未获授权的远端/发布操作 |
| 开发 AI | 执行当前包、必要重构、补必要回归、落盘开发小结、逐项整改 | 扩做下个包；改审核/终审记录；私改验收口径；把开发完成当终审 |
| 审核 AI | 阅读真实变更、独立运行适用检查、报告缺陷、记录复审和结论 | 只看开发小结就判通过；代开发改实现；省略失败和未执行项；放行后续版本 |

这是手工复制交接或独立 AI 会话均可执行的协议，不要求同时运行多个 AI。默认串行，一个任务包只允许一个开发写入者；审核期间冻结实现。发现新变更，原审核失效，需重新绑定基线复审。

## 2. 标准循环

1. 统筹：在当前版本任务台账写明“已下发”、验收条件、依赖、证据要求。
2. 开发：先读仓库状态，记录基线；只做本包；执行适用检查；将小结写入 `rounds/<任务包>_R01_开发小结.md`，状态改“待审核”。
3. 审核：核对开发给出的提交/文件哈希，检查真实差异；独立复验；写 `rounds/<任务包>_R01_审核小结.md`。
4. 审核结论只有“通过”“退回整改”“待验证”。有阻断问题则退回，环境不足导致必做检查未跑则待验证，均不能写成通过。
5. 开发整改写R02开发小结，审核写R02审核小结。旧轮次文件保留，不覆写原结论。关闭审核问题时记录证据，不只写“已解决”。
6. 审核通过后，在已下发范围内交回开发执行同版下一包；未下发则回交统筹。统筹可以一次预授权同一版本的一段任务顺序，使开发与审核直接轮流，无需每轮插入统筹。包间有依赖的，上一包通过才可继续；不允许据此开启下一版本。当前只有V015-M0已下发，M0通过后先由统筹检查隔离证据，再决定是否批量下发本版剩余包。
7. 所有包通过后，统筹独立终审，写 `03_终审与版本准入.md`，明确允许/禁止进入哪个版本。版本号变更与发布不自动发生。

包状态：待下发 → 已下发 → 开发中 → 待审核 → 审核通过；分支为整改中/待验证，回到待审核。

版本状态：规划锁定 → 已批准启动 → 开发与审核交替 → 待终审 → 终审通过。终审不通过回到整改中。终审通过和生产发布分别记录。

## 3. 落盘与证据

版本固定目录：

```text
doc/V0.x.y/
  01_实施方案与任务包.md
  02_任务台账.md
  03_终审与版本准入.md
  rounds/                 # 按任务包、轮次分开的开发/审核小结
  evidence/               # 可复核结果、指标、命令、哈希清单；不放密钥和个人信息
```

小结要短、证据要完整。详细日志与数据写evidence，小结只链接必要证据。证据记录：代码提交ID；无提交时记录工作区文件内容SHA256及差异摘要；数据库revision/只读快照哈希；配置哈希、模型名称/版本、评测集版本/划分；命令、环境、退出码、通过/失败/跳过数和时间。不可仅凭截图或“测试通过”一句话。

落盘的旧结论不得静默篡改。补充说明另开修订或追加勘误，标明旧证据失效原因。任务范围与验收条件在开发前锁定，开发中变更交统筹批准。

## 4. 开发、审核与终审要求

- 每个修复先确认问题与实际影响；审核报告中的F编号是调查起点，允许发现原判断不成立，但须给出证据并请统筹裁决，不能盲修或静默删项。
- 必要回归围绕业务风险设计：同名不同规格、否定、未知、专业别名、硬约束、权限、导出、反馈、缓存一致性等。不能为数量写镜像实现的低价值测试。
- 测试必须使用临时路径或专用脱敏快照；不得把生产账号库、当前物料库、全局规则文件直接当可写fixture。运行模块前检查导入副作用。模型/LLM下载和付费调用应有明确预算与授权。
- 审核至少检查：范围、真实diff、关键分支与异常、回归、数据兼容、权限、性能影响、迁移/回滚、文档契约。适用项说明方法；不适用说明原因。
- 任何未闭合P0/P1阻断本包及版本终审。P2只有统筹明确记录原因、后续包、期限/触发条件和防护后才可延期；影响当前验收的P2仍阻断。
- 必做检查受环境阻碍时状态为待验证，先做不受影响工作；禁止以AST定向探针、Mock结果或历史截图代替完整服务/模型验收。
- 算法改动必须同数据快照、同配置、同硬件预算比较；测试集不参与调参。金标变更有逐条原因，保留旧版本对照。无收益实验可关闭，但不得包装为已提升。
- 终审要抽查实际代码和至少一组关键证据，复核跨包契约、未闭合问题、版本与回滚材料。仅收齐小结不能算终审。

## 5. 极简交接（复制给对方，最多8行）

开发 → 审核：

```text
【开发→审核】V0.1.5 / V015-M0 / R01
基线：<commit或文件哈希清单>
完成：<1～2句>
验证：<实际通过/失败/未执行>
落盘：doc/V0.1.5/rounds/V015-M0_R01_开发小结.md
请复核：<关键点；只审本包>
```

审核 → 开发或统筹：

```text
【审核→开发/统筹】V0.1.5 / V015-M0 / R01
结论：通过 / 退回整改 / 待验证
问题：<编号+一句话；无则“未发现阻断问题”>
证据：<实际复验结果>
落盘：doc/V0.1.5/rounds/V015-M0_R01_审核小结.md
下一步：<整改或交统筹，禁止自行跨版本>
```

统筹下发/终审：

```text
【统筹】<版本>/<任务包>
裁决：<下发/整改/终审通过/不通过>
依据：<落盘路径>
边界：<允许做的任务；后续版本仍锁定或明确批准版本>
```

## 6. 初始准入

本轮只编制计划、整理目录并建立协议，不声称完成任何功能修复。

统筹批准 V0.1.5 启动，初始仅下发 `V015-M0`（测试隔离与可复验环境）。V0.1.6～V0.2.0均锁定，必须有前一版本终审批准记录才能进入。生产部署、实际密钥轮换、真实物料重编码等不因计划获批而自动获授权。
