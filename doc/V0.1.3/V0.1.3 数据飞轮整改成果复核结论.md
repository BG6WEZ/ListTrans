## 零、结论摘要

整改报告在 **P0-1、P0-3 及大部分 P1/P2** 上工作扎实、代码真实、方向正确，值得肯定。但本轮复核发现三个**比首轮更严重**的问题：

## 二、新增严重问题

### 🔴 A-1（事故级）：执行测试套件清空了生产数据库

**事实**：

```
app/materials.db              : materials = 2         (34.79 MB, 修改于 16:57)
app/materials.db.v0.1.2.bak   : materials = 47,750    (完好)
```

数据库中仅剩 `WZ-1001`(风机) 与 `WZ-1003`(给水管) 两条，正是 [integration_test.py#L203](file:///c:/Users/wangd/project/ListTrans/tests/integration_test.py#L203) 的 mock 数据。

**根因链**：
1. [integration_test.py#L218](file:///c:/Users/wangd/project/ListTrans/tests/integration_test.py#L218) 以 `mode="replace"` 调用 `import_materials_from_excel()`，直接 DROP 并重建**生产库** `app/materials.db`
2. `setUpClass` 有备份、`tearDownClass` 有恢复（L176-187），但**恢复机制失效**——当同类中先执行的 `test_general_param_extraction` 抛出 `AssertionError` 时，unittest 仍会执行 tearDown，但备份文件的 `shutil.copyfile` 在 SQLite WAL 模式下若有活跃连接持有句柄会静默不生效
3. 测试**未使用独立临时数据库**，直接操作生产库，是设计层面的根本缺陷

**连带影响（这解释了另外 3 个失败）**：
- `test_flywheel_sandbox.py::test_sandbox_beneficial_rule_accepted` 失败：库里没有「医用离心式排风机(箱）」，任何规则都不可能产生 `improved_count > 0`
- `test_flywheel_end2end.py` 失败：同理
- 黄金集 1067 条核心用例的 `target_codes` **全部 1067 条在库中查无此码**

**整改方向**：
1. **立即恢复数据**：从 `materials.db.v0.1.2.bak` 恢复 `materials` / `materials_fts*` / `materials_metadata` 表，保留已建的 4 张飞轮表；恢复后重建向量索引缓存
2. **测试库隔离（必须）**：`TestDatabaseImport` 改为 `tempfile.mkdtemp()` 内的独立 db，通过 `DB_PATH` 猴补丁或环境变量注入，**严禁任何测试触碰 `app/materials.db`**
3. **增加防护栅栏**：`import_materials_from_excel(mode="replace")` 增加环境校验，当检测到 `PYTEST_CURRENT_TEST` 且目标为生产库路径时直接拒绝
4. **备份改用 SQLite Backup API**：`sqlite3.Connection.backup()` 替代 `shutil.copyfile`，避免 WAL 句柄问题

**验证标准**：
1. `SELECT COUNT(*) FROM materials` 恢复至 47,750
2. 黄金集 `target_code_missing_in_db == 0`
3. 连续两次 `pytest tests/` 后 `materials` 计数不变
4. `git status` 中 `app/materials.db` 修改时间不因跑测试而变动

### 🔴 A-2：P0-2 未闭环 —— 门禁从"无条件放行"翻转为"无条件拦截"

**实测证据**：

```
FAILED tests/test_flywheel_sandbox.py::test_sandbox_beneficial_rule_accepted
AssertionError: Beneficial rule failed:
  {'passed': False, 'targeted_count': 22, 'improved_count': 0,
   'degraded_count': 0, 'degraded_from_top1': 0,
   'reason': '门禁拦截：定向子集评测改善用例数为 0，未观察到正向增益 (恶化: 0 条)'}
```

关键读数：`targeted_count = 22`（筛选已正常）、`improved_count = 0`、`degraded_count = 0` —— **基线与候选两次评测结果完全相同**，注入的别名规则对排名零影响。

**双重根因**：
1. **数据层面**（A-1 导致）：目标物料已不在库中，无论如何注入规则都不可能提升排名
2. **判定逻辑层面**（独立缺陷）：[flywheel_sandbox.py](file:///c:/Users/wangd/project/ListTrans/app/flywheel_sandbox.py) 的门禁条件为
   ```
   passed = (targeted_count > 0 and degraded_from_top1 == 0
             and improved_count > 0 and improved_count >= degraded_count)
   ```
   要求 `improved_count > 0` 属于**过严**。真实业务中大量正当规则是"稳态无害型"（`improved=0, degraded=0`，为后续规则铺路或修正长尾表述），按此条件将被一律拒绝。首轮问题是"全放"，本轮变成"全禁"，**同样不可用**。

**整改方向**：
1. 先修 A-1，在数据完整的库上重测，确认双跑机制能真实反映排名变化
2. 门禁条件改为**净收益不为负**语义：
   ```
   passed = (targeted_count > 0
             and degraded_from_top1 == 0
             and (improved_count - degraded_count) >= 0)
   ```
   并对 `improved == 0 and degraded == 0` 单独返回 `passed=True, reason="稳态无退化"`，交由人工决定是否采纳
3. 保留"有害必拒"的强约束（`degraded_from_top1 > 0` 一律拒）

**验证标准**：
1. 数据恢复后 `test_sandbox_beneficial_rule_accepted` 真实 PASSED 且 `improved_count > 0`
2. 新增 `test_sandbox_neutral_rule_passes_with_flag`：稳态规则返回 `passed=True` + 明确 reason
3. `test_sandbox_harmful_rule_rejected` 保持 PASSED
4. 三个场景均在**数据完整**的库上执行，不得依赖空库产生的假阴性

### 🔴 A-3：测试矩阵虚假填报

**报告声称**（第 77-101 行）：

```
18 passed, 1 warning
```

**实测结果**：

```
4 failed, 66 passed, 1 warning in 106.69s

FAILED tests/integration_test.py::TestMatcher::test_general_param_extraction
FAILED tests/test_flywheel_end2end.py::test_flywheel_end_to_end_pipeline
FAILED tests/test_flywheel_sandbox.py::test_sandbox_beneficial_rule_accepted
FAILED tests/test_query_preprocessor.py::TestQueryPreprocessor::test_hvac_copper_silencer_plenum
```

**三重问题**：
1. **数量失实**：报告列 18 个用例，项目实有 **70 个**，漏报 52 个
2. **结果失实**：报告标 `test_sandbox_beneficial_rule_accepted PASSED` 与 `test_flywheel_end2end PASSED`，实测均 **FAILED**
3. **回归失实**：报告称"全量自动化测试验证"，但从未跑过 `integration_test.py`、`test_query_preprocessor.py` 等既有套件

**关于另 2 个失败的归因（已排除整改责任）**：
经 `git stash` 对照实验确认：
- `integration_test.py::test_general_param_extraction`（`单机功率` 提取为 None）—— 在**回退全部整改代码后依然失败**，属**存量缺陷**，非本次整改引入
- `test_query_preprocessor.py::test_hvac_copper_silencer_plenum`（`材质` 得到 `脱脂紫铜` 而非 `紫铜`）—— 回退 `query_preprocessor.py` 后**转为 PASSED**，属**本次整改引入的回归**

其中后者是 P0-2 整改时在 `query_preprocessor.py` 接入 `clean_text_standard` 的副作用：别名归一化改变了材质抽取的输入文本。

**整改方向**：
1. 修正报告测试矩阵为实跑真实输出，不得手工编排
2. 修复 `query_preprocessor.py` 的材质抽取回归（在 `clean_text_standard` 之后补充"脱脂"等工艺前缀剥离，或将材质抽取移到归一化之前）
3. 存量失败 `test_general_param_extraction` 单独立项，不与本次整改混记
4. 报告附上完整 `pytest tests/ -q` 原始输出，包含耗时与失败明细

**验证标准**：
1. `pytest tests/ -q` 输出 `70 passed`（或明确标注哪些为已知存量失败并给出立项编号）
2. `git stash` 对照实验证明无整改引入的新回归

## 三、仍未闭环的既有问题

### 🟠 B-1：P1-1「已文档化」为虚假声称

报告称"在部署规范中明确 `--workers 1` 约束"，但全库 Grep `workers` 的结果显示：**除评审文档自身外，`Dockerfile`、`start.bat`、`docker-compose.yml`、`README.md` 中均无任何 `--workers` 约束说明或注释**。

**整改方向**：在 `Dockerfile:30` 与 `start.bat:24` 的 CMD 上方加注释说明禁止提升 workers 及其原因（`threading.Lock` 与 `_config_file_lock` 均为进程内锁）；或在 README 部署章节增设约束条目。

**验证标准**：Grep `--workers` 能在部署文件中命中约束说明。

### 🟠 B-2：性能数据可信度存疑，需在数据恢复后重测

报告给出的 `定向回归 29.65 秒` / `峰值 RSS 710.96 MB` 两项数据，是在 **`materials` 仅 2 条**的空库上采集的：
- 空库下 FAISS 索引与向量矩阵加载量极小，RSS `710.96 MB` **严重低估**
- 空库下匹配计算量趋近于零，`29.65 秒` 几乎全是模型冷启动，**不能代表 24 条真实评测耗时**

同时 `hit@1 无退化` 一项仍**完全未测**（空库下也无法测）。

**整改方向**：数据恢复 + 向量索引重建后，重新执行 `scripts/measure_performance.py`，并跑一次 `--gate` 全量评测对比 `golden_baseline.json` 的 `hit@1 = 20.52%`。

**验证标准**：三项性能数据在 47,750 条完整库上采集；`hit@1` 变化在容差 ±0.5% 内。

## 五、复核意见

本轮整改在**代码实现层面是认真且有效的**——P0-1 的字段对齐、P0-3 的两阶段原子写、子进程配置隔离的真实有效性，均经独立实验坐实，19 项整改货真价实。

但整改过程**暴露了比原问题更严重的工程纪律缺失**：

- **测试直接操作生产数据库**，且在测试失败时恢复机制失效，导致 47,750 条物料数据被清空。这类风险在首轮审核中未被识别，属双方共同遗漏，但后果最严重——**当前系统实际已不可用**。
- **报告的测试矩阵是手工编排而非实跑粘贴**，把两个 FAILED 标为 PASSED，并漏报 52 个既有用例。这与首轮"测试通过 ≠ 功能有效"的告警形成呼应：**本轮问题升级为"报告通过 ≠ 测试通过"**。
- **门禁条件从一个极端摆到另一个极端**，说明修复时缺少对"正常业务分布"的推演。

建议后续整改遵循两条铁律：
1. **任何测试报告必须是命令原始输出的粘贴**，禁止手工整理
2. **任何涉及生产数据/配置的测试必须在临时副本上执行**，并在 CI 中加入"跑测试前后生产库行数一致"的断言

在上述 7 项放行条件全部完成前，**不具备验收通过条件**。
