## 二、不符合要求的问题清单

### 🔴 P0-1：`--filter-keyword` 字段名错误，定向筛选永远返回 0 条

**问题**：[eval_golden_set.py#L205-210](file:///c:/Users/wangd/project/ListTrans/tests/eval_golden_set.py#L205-L210) 按 `x.get("raw_name")` 与 `x.get("raw_spec")` 过滤，但黄金集 `golden_set_v1.json` 的 item 字段实为 `name` 与 `specification`。

**实测证据**：
```
core 1067
has_raw_name: 0        # 1220 条中零条含 raw_name 字段
has_raw_spec: 0
filter_by_raw_name_result 0      # --filter-keyword "PAF-10" → 0 条
actual_impl_result_for_排风机 0   # --filter-keyword "排风机" → 0 条
would_match_if_using_name 24     # 若改用 name/specification → 24 条
```

即：**任何关键词传入都必然得到空集**。同理 `--case-ids` 中的 `x.get("idx")` 也不存在该字段（`has_idx: 0`），只有 `id` 分支可用。

**影响**：这是整个 Phase 2 门禁的输入源，直接导致 P0-2。

**整改方向**：
- 将 `raw_name` → `name`、`raw_spec` → `specification`
- 移除或修正 `idx` 分支
- 建议同时匹配 `target_ref[].db_name`，覆盖"标准名侧"关键词

**验证标准**：
1. `python tests/eval_golden_set.py --filter-keyword 排风机 --output-json out.json` 输出条数 = 24
2. 新增单测断言 `--filter-keyword` 对至少 3 个真实词返回非空
3. `--case-ids GT-0001,GT-0002` 精确返回 2 条

### 🔴 P0-2：沙箱回归门禁完全空转，无条件放行

**问题**：[flywheel_sandbox.py#L122-137](file:///c:/Users/wangd/project/ListTrans/app/flywheel_sandbox.py#L122-L137) 三重叠加缺陷：

1. **输入恒空**：受 P0-1 影响，`rows` 恒为 `[]`，`targeted_count = 0`

### 🔴 P0-3：采纳/回滚的文件写与数据库事务非原子，异常可致状态撕裂

**问题**：[server.py#L1535-1561](file:///c:/Users/wangd/project/ListTrans/app/server.py#L1535-L1561) 在 `with get_db_cursor(commit=True)` 事务内穿插 `atomic_write_json_config()` 文件写：

- 若第 1550 行文件写成功、第 1556 行 UPDATE 抛异常 → DB 回滚，**但 alias_dict.json 已被改写**，配置已生效而快照记录消失，规则无法回滚
- 反之若快照 INSERT 成功但文件写失败 → 快照标记 `is_active=1` 却对应未生效的规则，后续回滚会把配置改成一个从未生效过的状态
- 回滚接口 [server.py#L1666-1684](file:///c:/Users/wangd/project/ListTrans/app/server.py#L1666-L1684) 同构问题
- 另：`trigger_all_config_reloads()` 在事务内调用，会触发 `calculate_text_similarity.cache_clear()`（10 万容量），在事务持锁期间做重活，加剧 SQLite 写锁争用

**整改方向**：
1. 调整为「先 DB 事务提交（快照 + 状态）→ 再文件写 → 再 reload」，文件写失败则补偿性回写 + 快照置 `is_active=0`
2. 或引入两阶段：快照记 `pending_apply`，文件写成功后再 `commit` 状态
3. `trigger_all_config_reloads()` 移出事务块

**验证标准**：
1. 注入故障（mock `atomic_write_json_config` 抛异常），断言 DB 无孤儿 `is_active=1` 快照且配置文件内容未变
2. 注入 UPDATE 失败，断言配置文件已回退到 `config_before`
3. 端到端测试补充上述 2 个异常路径用例

### 🟠 P1-1：沙箱锁类型偏离计划（`threading.Lock` vs `asyncio.Lock`）

计划第 124 行要求 `asyncio.Lock()`，实现为 `threading.Lock()`（sandbox:23）。

**技术判定**：因沙箱在独立后台线程执行（`threading.Thread`，sandbox:186），`asyncio.Lock()` 在此反而不适用，**当前实现在技术上是正确选择**。且 Dockerfile:30 与 start.bat:24 均无 `--workers`，单进程内线程锁有效。

**问题在于报告未说明这一偏离的理由**，容易被误读为未按方案实施。

**整改方向**：在报告中补充设计变更说明；同时补充"多 worker 部署下锁失效"的运维约束声明（当前单 worker 前提必须写入部署文档）。

**验证标准**：部署文档明确禁止 `--workers > 1`，或改为基于数据库/文件的跨进程锁。
