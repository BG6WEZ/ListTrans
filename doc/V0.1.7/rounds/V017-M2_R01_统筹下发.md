## 二、本包调查起点（只读源码事实与 F14～F17）

1. **F14（DB Revision 缺失、缓存失效不统一与共享可变对象）**：
   - `app/db_manager.py:51`（`_HAS_FTS_CACHE`）、`:345-354`（`@lru_cache` 与 `_search_materials_keyword_cached`）返回共享可变 `Dict`/`List[Dict]` 对象，调用方若就地修改（如 `matcher.py` 注入临时字段）会污染全局缓存；且缓存未绑定统一单调递增或内容摘要级 `db_revision`。
   - `app/vector_index.py:834`（`check_db_timestamp_and_build`）依赖文件 mtime（`db_timestamp.txt`）判断新鲜度，同秒内写入、局部补参、重解析或替库可能误判为最新。
2. **F15（`load_cache` / `build_index` / `save_cache` 非原子快照与并发撕裂）**：
   - `app/vector_index.py:296-399`、`713-745`、`797`：内存中的 `index_to_material`、`numpy_embeddings`、`faiss_index` 分步替换，磁盘保存亦非整包原子提交，并发查询可能读到错位映射/向量；模型维度变化或构建失败时必须明确重建且保留可用旧快照。
3. **F16（未使用/非安全增量入口）**：
   - `app/vector_index.py:746-770`（`add_to_index`）无锁、不去重、不同步 `db_revision` 与磁盘缓存，存在静默漂移风险；须明确修复为受控一致路径或显式撤除并清理残留引用。
4. **F17（同码 append FTS 旧词残留与失败发布半成品）**：
   - `app/db_manager.py:1187`、`1402`、`1735` 等写入/补参/重解析路径中，同 `code` 重复 append/upsert 若未先清除旧 `materials_fts` 词条，会残留过期 FTS 记录；写入或索引发布失败时严禁对外暴露半成品状态。

## 三、必须实现的契约（M2-C01～C06）

| 编号 | 契约名称 | 必须满足 |
|---|---|---|
| M2-C01 | 统一 `db_revision` 与全链路缓存失效 | 在 `materials_metadata` 维护单一事实源 `db_revision`（每次导入、append、补参、全量/局部重解析、替库/恢复均原子推进）；`db_manager` 查询缓存、`_HAS_FTS_CACHE` 与 `vector_index`（含 `cache_metadata.json`）均绑定 `db_revision`，消除仅靠文件 mtime 的失效盲区；确保导入、补参、重解析、替库、进程重启后各层读到同一版本。 |
| M2-C02 | 读返回去共享可变对象 | `db_manager` 所有缓存读入口（`get_material_by_code`、`_search_materials_keyword_cached` 等）与 `vector_index` 读视图返回隔离副本或不可变快照视图，修改返回值绝不污染后续调用方或进程内缓存。 |
| M2-C03 | 向量索引原子快照、维度校验与失败保旧 | 内存采用不可变快照对象（打包 `db_revision`、`model_name`、`dimension`、`materials`、`numpy_embeddings`、`faiss_index`）单引用原子切换，并发 `search` 与 `load`/`build` 绝不出现映射与向量错位；磁盘 `save_cache` 采用临时目录/临时文件落盘后原子替换；模型或维度变化明确触发完整重建；任何构建/保存/加载异常均保留上一可用旧快照，不发布半成品。 |
| M2-C04 | `add_to_index` 增量入口治理（F16） | 全面排查 `add_to_index` 调用方：若无真实业务依赖则显式撤除（或改为受控异常/委派一致重建）；若保留则必须加锁、同码去重、绑定 `db_revision` 与原子快照切换，并补专项并发/一致性测试。 |
| M2-C05 | 同码 append/更新 FTS 无旧词与失败原子回滚（F17） | 同码重复 append、单条更新、局部/全量重解析后，`materials_fts` 中该 `code` 仅存在最新分词记录，无旧词残留且行数与 `materials` 一致；任意阶段失败（DB 写入/FTS 更新/向量保存）回滚且对外保持旧版可用状态。 |
| M2-C06 | 既有门禁不退化、范围与隔离红线 | 保持 V0.1.5/V0.1.6/V017-M0/M1 既有契约、三规则门禁（18 组 `score_diff_count=0`、`GT-0674/0677/0678` 维持 `recommended`）与 M1 内部参考底线不退化；严禁扩做 `V017-M3`（同步卸载/队列限额/清理策略），严禁调打分权重/阈值；遵守全隔离环境变量与仓外 `--basetemp`，外层 35 项业务资产与冻结夹具 0 字节变化。 |

## 四、最低验收矩阵（开发自验与独立审核必查）

1. **版本一致性端到端**：隔离库上依次执行导入 → 补参/更新 → 局部/全量重解析 → 替库 → 模拟重启，断言 `db_revision` 单调推进且 `db_manager` / `vector_index` / 磁盘 `cache_metadata.json` 读到同一版本。
2. **不可变读隔离**：修改 `get_material_by_code` / 关键词检索 / 向量检索返回字典及嵌套 `attrs`，再次查询断言缓存原值未被污染。
3. **并发与失败保旧**：多线程并发 `search` + `build_index`/`load_cache` 压测无错位/越界/异常；注入磁盘写失败或编码失败，断言旧内存快照与旧磁盘快照完好可用；模拟模型维度变化（如 512 ↔ 384），断言明确重建而非静默加载错维缓存。
4. **增量入口与同码 FTS**：验证 `add_to_index` 撤除或一致性行为；对同一 `code` 重复 append/更新不同规格词，断言 FTS 查旧词命中 `0`、查新词命中 `1`、`COUNT(materials_fts) == COUNT(materials)`。
5. **全量 pytest、三规则门禁与隔离**：Windows 隔离 `--basetemp` 全量 pytest（`>=395` + M2 新增）全通过、`EXIT=0` 并落盘日志；三规则门禁 18 组 `score_diff_count=0`、`EXIT=0`；`verify_isolation.py` 前后 PASS，外层 35 项业务资产与冻结夹具 0 字节变化。
6. **交付基线完整性**：落盘 `doc/V0.1.7/rounds/V017-M2_R01_开发小结.md` 与 `doc/V0.1.7/evidence/m2_r01_delivery_hashes.md`（**必须涵盖全部改动与新增的 `app/` 与 `tests/` 文件最终 SHA256，最后一次测试修改后重新生成哈希**）。
