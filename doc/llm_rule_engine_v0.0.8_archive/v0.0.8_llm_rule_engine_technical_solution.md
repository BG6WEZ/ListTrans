## 一、新功能评估报告

针对目前系统通过开发人员硬编码清洗与比对规则带来的“效率低、维护成本高、系统臃肿”等问题，拟引入大模型（LLM）实现普通业务员工通过自然语言交互自动生成匹配规则。对该新功能的评估如下：

### 1.1 可用性评估 (Usability) - ⭐⭐⭐⭐⭐ (极高)
*   **零代码门槛**：非程序员（如暖通、电气、给排水专业工程师及采购员）只需使用自然语言描述清洗逻辑（如：“针对风机盘管，如果包含‘双吹’，则清洗提取为...”），大幅降低使用门槛。
*   **高可读性与可维护性**：系统将 LLM 输出的抽象逻辑编译为**可视化的结构化规则卡片**（包含：清洗触发词、关键提取属性、排除/必含比对条件）。员工可直观阅读、理解并手动微调参数。
*   **实时试运行与反馈机制**：提供在线样本测试控制台，在提交审核前，员工可用真实原文测试规则效果，确保“所见即所得”。

### 1.2 可落地性评估 (Feasibility & Practicability) - ⭐⭐⭐⭐⭐ (极高)
*   **零在线推理延迟（匹配无损）**：LLM 仅在“**规则生成与调试阶段**”被调用。规则审核通过后，编译为标准的**声明式 JSON DSL 规则**，在物料比对阶段由本地 Python 解释器高效执行，比对性能保持在毫秒级，**不增加批量匹配的响应耗时与 API 消耗费用**。
*   **完善的审核风控闭环**：基于系统现有的 RBAC 权限体系（`employee` / `manager` / `director` / `admin`），构建“草稿生成 -> 样本测试 -> 提交审核 -> 经理/总监批准 -> 动态加载”的全生命周期，确保入库规则质量。
*   **多模型优先容灾保障**：大模型调度层支持多厂家（如 DashScope 阿里云、DeepSeek、OpenAI 兼容接口等）优先顺序配置与超时自动降级（Fallback），保障规则生成功能的高可用。

### 1.3 业务价值与 ROI 评估 (Value & ROI) - ⭐⭐⭐⭐⭐ (极高)
*   **规则迭代效率提升 90%+**：规则创建与上线周期从传统的“沟通需求 -> 开发编码 -> 部署上线（数天/周）”缩短至“自然语言描述 -> 测试审核（数分钟）”。
*   **解耦架构与系统瘦身**：将散落在 `preprocessor.py` 和 `domain_extractors.py` 中的硬编码正则表达式与条件判断剥离，核心比对引擎保持极简与纯粹。
*   **专业隐性知识数字资产化**：将资深专业工程师的清洗比对经验标准化沉淀为可统计、可审计、可共享的系统规则库。
*   **匹配率持续演进**：长尾设备与特定专业物料的自动匹配率随规则库丰富呈持续上升趋势。

## 三、核心模块详细设计

### 3.1 规则 DSL 声明式规范 (Rule Schema Protocol)

LLM 生成的规则将严格遵循以下 JSON Schema 标准格式，便于前端可视化编辑与后端无缝执行：

```json
{
  "rule_id": "RULE-2026-HVAC-001",
  "rule_name": "暖通离心式水冷机组制冷量提取与特征过滤规则",
  "scope_level": "category",
  "scope_target": "离心式水冷机组",
  "discipline": "暖通",
  "priority": 10,
  "description": "针对原文包含‘离心机’或‘水冷机组’时，清洗去除无用前缀，提取制冷量(kW/RT)与冷媒类型，强制排除螺杆机组物料。",
  "cleaning_rules": [
    {
      "action": "regex_replace",
      "pattern": "高效(变频)?离心式",
      "replacement": " 离心式 ",
      "description": "规范化离心机词首"
    },
    {
      "action": "synonym_replace",
      "target": "冷水机",
      "replacement": "水冷机组"
    }
  ],
  "extraction_rules": [
    {
      "key": "cooling_capacity_kw",
      "label": "制冷量(kW)",
      "pattern": "(\\d+(?:\\.\\d+)?)\\s*(kW|千瓦|RT|冷吨)",
      "unit_convert": {"RT": 3.517, "冷吨": 3.517, "kW": 1.0, "千瓦": 1.0}
    },
    {
      "key": "refrigerant",
      "label": "制冷剂",
      "pattern": "(R134a|R1234ze|R32|R410A)",
      "default_value": "R134a"
    }
  ],
  "matching_rules": {
    "must_contain": ["离心"],
    "must_not_contain": ["螺杆", "风冷"],
    "score_boost_keywords": {"高压离心": 15.0, "磁悬浮": 20.0}
  },
  "test_cases": [
    {
      "input_text": "高效变频离心式水冷机组 1200kW R134a 380V",
      "expected_extracted": {"cooling_capacity_kw": 1200.0, "refrigerant": "R134a"}
    }
  ]
}
```

### 3.2 大模型优先调度与多厂家容灾机制 (Multi-Vendor LLM Router)

在管理员控制台 (`web/admin.html`) 中可配置多厂家大模型信息，核心逻辑如下：

1. **多厂家配置项**：
   * `provider_id`: 唯一标识 (如 `qwen-max`, `deepseek-v3`, `qwen-plus`)
   * `name`: 显示名称 (如 "阿里云 Qwen-Max", "DeepSeek-V3")
   * `base_url`: API Base URL (如 `https://dashscope.aliyuncs.com/compatible-mode/v1`)
   * `model_name`: 模型标识符 (如 `qwen-max`, `deepseek-chat`)
   * `api_key`: 加密存储的 API Key
   * `priority`: 调度优先级 (1 为最高，数字越小优先级越高)
   * `timeout_seconds`: 单次请求超时时间 (默认 8 秒)
   * `is_active`: 启停状态 (1/0)

2. **自动故障转移 (Failover Execution Flow)**：
   ```
   [请求生成规则] -> 按 Priority 升序获取 active providers
                         |
                         v
                [尝试调用 Provider N]
                         |
           +-------------+-------------+
           | (成功 200)                 | (超时 / HTTP 5xx / API 异常)
           v                           v
      [返回规则 JSON]           [记录失败/超时日志]
                                       |
                                       v
                             [自动切换调用 Provider N+1]
                                       |
                               (若全部失败 -> 抛出友好的网络降级提示)
   ```

3. **管理员界面扩展**：
   * 在管理员页面 (`admin.html`) 中新增 “大模型服务管理” 标签页，支持增删改查模型节点、调整优先级顺序、测试连通性，并查看各模型的**调用总次数、成功率、平均响应时延与故障切频统计**。

### 3.3 规则生命周期与审批工作流 (Audit & Governance Workflow)

```
   [员工 (Employee)]
         | (1) 自然语言描述 + Prompt
         v
   [LLM 自动生成 JSON DSL]
         | (2) 界面可视化查看 + 样本调试微调
         v
    [状态: Draft (草稿)]
         | (3) 点击 "提交审核"
         v
 [状态: Pending_Approval (待审核)]
         |
         +---------------------------------------+
         |                                       |
         v (4a) 经理/总监 点击 "批准"             v (4b) 经理/总监 点击 "驳回"
 [状态: Approved (已批准)]                [状态: Rejected (已驳回)]
         |                                       |
         v (5) 自动加入系统 active 规则池          v (退回员工可重新修改提交)
  [动态加载引擎生效]
```

* **权限约束**：
  * 普通员工 (`employee`)：只能创建、编辑自己的草稿，提交审核，查看规则列表与命中统计。
  * 部门经理/总监 (`manager`, `director`)：拥有规则审核权（批准/驳回/修改建议），可强制停用或废除不良规则。
  * 系统管理员 (`admin`)：拥有全量规则管理权限及大模型底层参数配置权限。

### 3.4 规则命中统计与性能归因 (Rule Hit Tracking)

* **统计指标**：
  * `hit_count`: 规则在清洗与匹配计算中被启用的累计总次数。
  * `last_hit_at`: 最近一次触发时间。
  * `matched_success_count`: 规则命中且最终成功置信匹配的次数。
* **高性能异步计数实现**：
  在内存中维护 `HitCounterBuffer`，每次清单匹配触发规则时仅更新内存计数器，每 60 秒或达到 100 次更新时统一异步批量写入 SQLite，避免数据库频繁 IO 锁表。
* **规则可视化排行榜**：
  在规则生成页面呈现“高频优秀规则 Top-10”与“零触发待优化规则”，指导业务人员持续治理规则库。

## 五、数据库 Schema 扩展设计

所有数据库表建在系统现有的 `app/materials.db` 与 `app/auth.db` 中：

### 5.1 大模型厂家配置表 (`llm_providers`) - 位于 `app/materials.db`
```sql
CREATE TABLE IF NOT EXISTS llm_providers (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    provider_id TEXT UNIQUE NOT NULL,       -- 如 'qwen-max', 'deepseek-v3'
    name TEXT NOT NULL,                      -- 厂家显示名称
    base_url TEXT NOT NULL,                  -- API Base URL
    model_name TEXT NOT NULL,                -- 模型标识
    api_key_enc TEXT NOT NULL,               -- API Key (加密)
    priority INTEGER NOT NULL DEFAULT 10,   -- 优先级 (1-100, 越小越优先)
    timeout_seconds REAL DEFAULT 8.0,        -- 超时秒数
    is_active INTEGER DEFAULT 1,             -- 启停状态
    total_calls INTEGER DEFAULT 0,          -- 调用的总次数
    total_successes INTEGER DEFAULT 0,      -- 成功次数
    total_failovers INTEGER DEFAULT 0,      -- 降级切频次数
    avg_latency_ms REAL DEFAULT 0.0,        -- 平均延迟毫秒
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME DEFAULT CURRENT_TIMESTAMP
);
```

### 5.2 智能规则定义表 (`llm_rules`) - 位于 `app/materials.db`
```sql
CREATE TABLE IF NOT EXISTS llm_rules (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    rule_id TEXT UNIQUE NOT NULL,           -- 规则编号，如 'RULE-2026-001'
    rule_name TEXT NOT NULL,                 -- 规则名称
    scope_level TEXT NOT NULL,               -- 'universal', 'discipline', 'category'
    scope_target TEXT,                       -- 作用目标（如 '暖通', '风机盘管'）
    discipline TEXT,                         -- 专业分类
    priority INTEGER DEFAULT 10,             -- 执行优先级
    description TEXT,                        -- 规则自然语言描述/说明
    rule_json TEXT NOT NULL,                 -- 完整的 Rule DSL JSON 内容
    author_id INTEGER NOT NULL,              -- 创建人 User ID
    author_name TEXT NOT NULL,               -- 创建人 Username
    status TEXT NOT NULL DEFAULT 'draft',    -- 'draft', 'pending_approval', 'approved', 'rejected', 'deprecated'
    hit_count INTEGER DEFAULT 0,             -- 规则累计命中/启用次数
    last_hit_at DATETIME,                    -- 最近一次命中时间
    approver_id INTEGER,                     -- 审核人 User ID
    approver_name TEXT,                      -- 审核人 Username
    approval_comment TEXT,                   -- 审核意见
    approved_at DATETIME,                    -- 批准上线时间
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME DEFAULT CURRENT_TIMESTAMP
);
```

### 5.3 规则审核履历表 (`rule_audit_logs`) - 位于 `app/materials.db`
```sql
CREATE TABLE IF NOT EXISTS rule_audit_logs (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    rule_id TEXT NOT NULL,
    action TEXT NOT NULL,                    -- 'create', 'submit', 'approve', 'reject', 'deprecate'
    operator_id INTEGER NOT NULL,
    operator_name TEXT NOT NULL,
    operator_role TEXT NOT NULL,
    comment TEXT,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);
```

## 七、V0.0.8 版本实施路线图与验证方案

### 7.1 开发阶段规划
1. **阶段一：数据库表与后端 DSL 引擎构建**
   * 创建 `llm_providers`, `llm_rules`, `rule_audit_logs` 表结构。
   * 实现声明式规则解释执行器 (`DynamicRuleInterpreter`)，继承整合现有的 `QueryPreprocessor` 和 `DomainExtractor`。
2. **阶段二：多厂家大模型优先路由与 Admin 配置**
   * 编写 `LLMProviderManager` 支持优先队列与故障自动切换。
   * 扩展 `admin.html` 与后台配置 API。
3. **阶段三：LLM 规则自然语言编译器与审核流**
   * 编写提示词 Prompt 模板与 JSON Parsing，实现 `/api/llm-rules/generate` 和 `/api/llm-rules/test`。
   * 实现审核工作流接口（提交、批准、驳回）。
4. **阶段四：前端 UI 导航与界面协同集成**
   * `index.html` 顶部增加 `LLM 规则生成` 导航标签页。
   * 构建规则生成 Studio、可视化微调卡片、试运行面板及审核工作台。
5. **阶段五：命中统计归因与全流程联调测试**
   * 异步计数刷盘机制与统计图表呈现。

### 7.2 验证方案
* **单元测试**：
  * 测试 `DynamicRuleInterpreter` 解析各类规则 JSON 的准确性与性能。
  * 测试 `LLMProviderManager` 在主模型超时/异常时的自动 Fallback 切换逻辑。
* **集成测试**：
  * 员工身份创建规则 -> 大模型生成 DSL -> 样本测试 -> 提交审核。
  * 经理身份登录审核 -> 审批通过 -> 验证清单比对时该规则成功生效并计入 `hit_count`。
* **性能测试**：
  * 验证加入 100 条动态 DSL 规则后，单行清单匹配耗时增加量不超过 2ms。
