## 2. M4-01：规则授权与状态机（F04）

先盘点所有规则写入口，包括`/api/llm-rules`的保存、修改、提交、审核、启停、删除；`/api/binding/rules/confirm`、规则删除等全局规则入口；飞轮accept/rollback等已有全局变更入口及其服务函数。逐项给出“路由—服务—身份来源—对象—允许状态”表。不能只隐藏按钮或只在路由加角色装饰器。

锁定角色语义如下，角色与用户ID必须来自服务端验证的有效账号；请求正文的author/role/status/approver等字段没有授权效力。直接调用业务服务也必须检查角色、所有权与前态，不能由一个无权限调用者借`user_info`字段变更全局规则。

| 操作 | 允许主体与前提 | 必须拒绝的情况 |
|---|---|---|
| 新建草稿、编辑/提交本人草稿或退回稿 | 有效employee/manager/director/admin，作者由服务端记录；待审稿修改先撤销本次提交 | 冒充作者、覆盖他人、正文直接写成已审核/已发布 |
| 审核同意/退回 | manager/director/admin；仅合法待审版本；审批者不能是该版本作者 | employee审核、自审、对草稿/已废弃版本直接同意 |
| 发布/启用 | admin；仅当前内容已被另一有效用户审核通过的版本；保持既有适用门禁 | 草稿/待审/退回/废弃直接toggle启用、旧审批覆盖新内容、employee或manager/director发布 |
| 停用/废弃全局生效规则 | admin，记录操作人与原因；停用后可重新启用的内容须保留有效审批 | 普通作者借启停/删除绕过审批或改变全局生效集 |
| 删除 | 作者可删本人未发布草稿/退回稿；全局历史规则由admin按明确策略停用/保留审计 | 删除他人、删活动规则后绕过审批重建；历史凭据无痕消失 |

admin身份不免除自审限制或内容一致性校验。可由admin发布本人创作、已由另一人审核的版本。若需管理员代编辑他人规则，必须走显式、可审计的代编辑权限，并成为该修订的作者、使旧审批失效；不能以通用update悄悄保留他人审批。

审批与激活分开：可以新增“已审核待发布”状态或等价字段，不要求特定状态名。不得审核同意即让非发布者的操作直接进入运行生效集。修改已发布规则的DSL、scope、priority、参数及其他影响执行的字段，必须形成待重新审核版本：可以立即停用原版，或保留原已审核版本并单独存新草稿；无论采用哪种实现，运行时只能读到已审核的同一内容。审批/启用绑定修订号或内容摘要，并在实际写入时原子核对；并发编辑后拿旧审批发布必须失败。缓存失效与事务提交一致，不得从另一入口再次激活未审核内容。

历史无审批来源的规则不得凭`status=approved`自动获得新审批资格；在隔离旧库样本中验证保守迁移/停用并提示重新审核。不得回填虚构审批人。真实现有规则库本轮只提供迁移方案，不直接迁移。普通员工仍可通过M2/M3有效凭据为本人清单人工确认/拒绝；这不等于写全局规则。对无审批流程的旧全局规则入口，至少限制为admin，员工提交只能产生不生效草稿；不得借本包关闭个人复核能力。

## 3. M4-02：任务所有权（F21）

上传任务、沙箱评测任务及其现有状态/结果读取入口，创建时持久或进程内记录服务端当前用户的稳定ID；不能信任请求owner、username或task_id的不可猜性。所有用户可达读取入口先鉴权再做owner核验，再返回状态、progress、result、report、error或下载内容；盘点若发现其他现有任务结果入口，采用同一检查。

默认仅创建者可读，**admin之间也不默认互读**；本包不新增跨用户管理查询。合法后台worker仅使用明确的内部执行路径，不得以“owner缺失表示内部任务”暴露HTTP旁路。历史缺失owner、用户删除/重建、未知ID均不得分配给当前请求者。拒绝响应不泄露结果/原文/错误栈；对已登录他人访问可统一403或404，但必须前后一致并记录口径。本人任务正例、两个employee交叉读取、两个admin沙箱交叉读取、缺失/伪造owner均须覆盖；UUID随机性不是授权证据。

## 4. M4-03：账号、Token与初始凭据（F22）

交付一份明确的生命周期表并实现以下不可降低的语义：

1. 改密、管理员重置、账号停用、角色变化后，该账号此前签发的所有Token不能继续访问受保护接口；账号删除后重建也不能承接旧Token。通过服务端凭据版本/等价机制核验，不只验JWT签名和exp；缺少新版本证据的旧Token保守失效。并发改密/签发不能重新放出旧版本Token。
2. 登出后被登出的Token立即失效，重新登录的新Token正常；撤销跨进程重启保持。默认撤销当前Token；若实现选择更严格的全会话登出，必须在UI/API文案与生命周期表明确，并验证其他会话也失效。不能采用仅删浏览器localStorage的策略。
3. 新建、批量导入、管理员重置产生的临时凭据必须唯一，不再使用统一默认口令或弱回退。临时秘密只能经明确的受控一次性渠道交付，不进入普通日志、证据、前端持久存储、代码或普通导出。生产缺少必要启动秘密时安全失败或进入明确的受控初始化流程，不以可猜默认值启动，不打印可复用管理员口令。
4. 首次/重置后强制改密：登录返回明确标志；完成前仅开放身份检查、改密、登出及必要初始化操作，其余业务API服务端拒绝。改密成功后旧临时凭据和旧Token失效，使用新凭据/新Token正常；不能只依靠前端弹窗。最小UI必须让用户实际完成改密、显示失效后重新登录提示。
5. 账号schema迁移在合成旧库上证明幂等、失败不半迁移，并注明旧账号首次改密标志的保守策略；不得批量重置真实现有密码。认证初始化/测试不得自动导入真实人员Excel或接触现有账号库。测试身份均合成，生产/测试模式鉴权旁路继续受现有护栏约束，不能通过AUTH_DEV_MODE绕过本轮验收。

密码/权限更改与凭据版本提交应原子一致。认证存储故障或撤销状态不可读时不得放行旧Token。失败登录、失败改密与无权重置不能变更账号、撤销别人的Token或泄露账号秘密。日志保留动作、操作者、对象和结果，屏蔽口令、JWT与敏感配置。
