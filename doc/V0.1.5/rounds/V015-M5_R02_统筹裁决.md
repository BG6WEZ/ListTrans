## 2. R03唯一整改范围

允许最小修改`server.py`导入监督/提交编排、`db_manager.py`暂存/提交/回滚、`vector_index.py`候选/缓存提交及必要测试和验证脚本。若确需修改共用边界模块，只限传递仲裁/清理所需，说明必要性并回归A-M5-03。不得扩做排序/金标/反馈治理、多worker架构或原生拒绝UI；真实.env、账号库/业务库与业务快照继续冻结。

### A-M5-01：同一次导入的成功发布或失败保留

- `replace`与`append`均受同等保护，覆盖数据库主表、FTS、元数据、内存向量和整套磁盘缓存。失败/取消终态必须保留可核验旧态；completed才允许各处一致为新态。append正常成功保留旧物料并正确增加/更新本次物料，不能为回滚便利改成丢旧数据的替换。
- 最终提交前完成解析、向量候选和缓存准备等可耗时/可失败工作；在全部资源达成稳定新态前不得销毁必要旧表、元数据、内存引用和缓存回滚材料。可以选择可逆交换/统一版本指针等实现，统筹不锁死具体算法。
- 缓存逐文件`os.replace`的“单文件原子”不等于整套原子。第1/第2/最后一份缓存切换失败、目标原来不存在、旧FAISS文件在新模式不再需要等情况均须考虑；不能留下混代文件或靠吞掉OSError宣布成功。回滚后重载缓存应仍对应旧DB；成功后重载对应新DB。
- SQLite提交失败、索引发布失败、缓存写入/替换失败须有一致的回滚或可核验恢复策略。若回滚本身失败，必须明确恢复失败并保持写入阻断/保留恢复材料，不能释放锁后继续接受导入、谎称已安全回滚。

### A-M5-02：取消与提交的唯一仲裁

- 建立监督线程和worker共同遵守的状态转换/仲裁点，例如`staging -> cancelled`或`staging -> committing -> committed/rolled_back`；仅在worker中加锁或重复检查event不足以解决监督线程同时标failed的竞态。
- 提交获准前取消/超时胜出：禁止发布，旧态保持；提交获准后监督线程不得继续异步将同一任务终结为“已取消/failed”，应真实显示提交/收尾状态，等待提交成功或受控回滚的唯一结果。不得简单无限延长超时、删除超时或永久屏蔽取消来凑通过。
- 进入提交门并不意味着任何异常都可宣称成功：若缓存等失败，仍按A-M5-01回滚；若已完成统一提交，迟到超时/取消不得把真实completed改failed。提交和回滚应有明确受控边界；重型工作放在准备阶段，避免把整个计算长期锁在不可取消段。
- 保持R02已通过的owner令牌语义：实际worker/提交/回滚未退出或隔离前，第二导入409；旧任务不能释放新任务锁。临时文件与暂存表清理、任务终态只在正确所有者下完成，不覆盖新任务。

## 3. 锁定复验矩阵

| 场景 | 必须观察的结果 |
|---|---|
| Probe A：Step5后/Step6前取消；提交门前取消对照 | 按唯一仲裁结果：取消胜出则各处全OLD；提交已获准则最终全NEW/completed或失败回滚全OLD，禁止failed+混态 |
| Probe B：真实0.25s超时落入Step5附近 | 超时监督与提交门不能双赢；任务终态与DB/FTS/metadata/内存/磁盘完全对应，不能只检查cancel_event或锁 |
| Probe C：Step7第二次os.replace抛OSError | 所有缓存、数据库和内存回到前态，任务失败可解释；再正常导入成功且重载缓存一致 |
| Probe D：append索引/保存失败 | DB/FTS/meta不残留APPEND-NEW，原数据与缓存不变；append正常成功也必须验证 |
| 其他提交边界/异常 | 用Event/barrier等确定性卡点覆盖SQLite提交、内存发布、缓存首/中/末文件切换及终态写回；除必要真实超时对照外，不依靠随机sleep碰运气 |
| 并发与恢复 | 旧worker/回滚仍存活时第二导入409，退出后新导入成功；旧任务晚到消息不改新任务或已确定终态；失败及成功后冷读缓存核验 |

每个测试保留前态/后态的主表、FTS、metadata、内存索引编码与缓存全文件摘要（含缺失/多余文件）、任务状态/原因和锁owner证据。采用合成数据与临时库，故障注入不能替换掉受测的提交/回滚本身。保留R01五项与R02原回归；不得删失败断言、金标难例或降低阈值。若确有错误预期，只能按仲裁契约逐条说明修正及覆盖去向，审核独立确认。
