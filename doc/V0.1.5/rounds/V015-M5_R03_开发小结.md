## 本轮完成

严格按 R03 统筹裁决第 2～3 节闭环 `A-M5-01` 与 `A-M5-02`，未调整任何既有物理硬约束、单位门禁、匹配权重或金标判定阈值，未扩做原生拒绝 UI 或后续版本任务：

1. **A-M5-02（P1）提交窗口唯一仲裁门与 `owner` 互斥延续（[app/server.py](../../../app/server.py#L2999-L3360)）**：
   - 新增 `ImportCommitArbiter`（`app/server.py:2999-3075`），通过单 `threading.Condition` 护卫 CAS 状态机 `staging -> cancelled` / `staging -> committing -> committed | rolled_back`，作为 worker 线程与超时监督线程的唯一仲裁点。
   - 门前（`staging`）超时或异常时，监督线程调用 `arbiter.request_cancel()`（L3281）胜出并置位 `cancel_event`，随后 worker 调用 `arbiter.begin_commit()`（L3181）必返回 `False` 并抛出 `ParseCancelledError`，禁止触碰任何活态资源。
   - 一旦 worker 在 Step 5 前通过 `arbiter.begin_commit()` 抢占进入 `committing`，后续超时触发的 `request_cancel()` 返回 `False`；监督线程不得再将该任务写为冲突的 `failed`/`cancelled`，而是通过 `arbiter.wait_terminal(timeout=_DB_IMPORT_COMMIT_SETTLE_SLICE_SECONDS)`（L3302-L3303）分片等待唯一终态。Step 6 在门内调用 `index_manager.publish_candidate(candidate, cancel_event=None)`（L3202）防止迟到取消打断；全层发布完成后调用 `arbiter.finish_commit()`（L3213），监督线程依 `COMMITTED` 写入 `status="completed"`（L3305-L3316），消除“真实已完成却被标 failed”。
   - 保留 R02 已验证的 `owner` 令牌互斥语义：`_release_db_lock_if_held(lock_token)` 仅在 worker 自身 `finally` 退出时释放（L3265），worker 存活期间监督线程不释放互斥锁（L3350-L3356），第二导入持续返回 `409`。
2. **A-M5-01（P1）`replace` 与 `append` 统一暂存-原子发布、五态联动回滚与缓存写阻断（[app/db_manager.py](../../../app/db_manager.py)、[app/vector_index.py](../../../app/vector_index.py)、[app/server.py](../../../app/server.py)）**：
   - **`replace` 与 `append` 同等 staging 保护**（`app/db_manager.py:921-1093`）：`import_materials_from_excel(..., stage_only=True)` 在 `replace` 和 `append` 两种模式下均先写入隔离的 `materials_stage` / `materials_fts_stage` 表；`append` 模式先按显式列清单镜像现役 `materials` 与 `materials_fts` 全量旧行至 stage 表，再 `INSERT OR REPLACE` 本批增量，并将合并后的 `total_rows`/`imported_rows`/`disabled_rows` 写入 `stage_handle`（L1079-L1089）。因此在准备阶段或 `build_index_candidate` 失败/取消（Probe D）时，旧物料表、FTS、元数据、内存与磁盘缓存零残留；成功时保留旧物料并发布合并新代。
   - **SQLite 保留旧代与唯一反向交换**（`app/db_manager.py:481-701`）：`_swap_materials_tables_exclusive(..., retain_old_generation=True)` 在单事务 `BEGIN EXCLUSIVE` 内将旧表重命名为 `materials_old`/`materials_fts_old`、stage 表提升为活态表、重建生产索引并更新 `materials_metadata`；仅在 Step 5～7 全部成功后由 `drop_retained_materials_old_generation()`（L616）清理旧代。若内存发布或磁盘缓存切换失败，worker 在 `COMMITTING` 异常处理分支（`app/server.py:3220-3250`）依次执行 `reverse_retained_materials_swap(previous_meta)`（单事务恢复旧表与 5 项元数据，无旧表时移除失败新代）与 `index_manager.rollback_published_state(mem_snapshot)`（`app/vector_index.py:458`，恢复深拷贝的内存映射、向量矩阵及 FAISS 引用），并调用 `arbiter.fail_commit(str(exc))` 收口到唯一 `rolled_back` 终态。
   - **缓存整套可逆切换与双失败写阻断**（`app/vector_index.py:59-89, 504-593`）：`commit_candidate_cache` 先将 `CACHE_FILE_NAMES`（`materials.index`、`materials_embeddings.npy`、`index_to_material.json`、`cache_metadata.json`）中现存的旧代文件整体移入同级 `.backup_<pid>_<tid>` 目录（覆盖目标文件原不存在、及新代不使用 FAISS 时清理陈旧 `.index` sidecar 场景），再逐文件 `os.replace` 提升 `.stage_*` 目录文件。若任一文件替换抛 `OSError`（Probe C），则调用 `_restore_cache_backup` 还原全部旧缓存并重抛异常驱动 DB/内存联动回滚；若恢复过程本身再次抛 `OSError`，则调用 `block_cache_writes()` 置位 `_cache_write_blocked = True`、保留 `.stage_*` 与 `.backup_*` 恢复材料不删除，并抛出 `CacheRollbackError`（后续缓存写入经 `_assert_cache_writable()` 持续拒绝，禁止在未人工恢复前继续导入或谎称已安全回滚）。
