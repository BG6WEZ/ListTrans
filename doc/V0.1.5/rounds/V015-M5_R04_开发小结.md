## 本轮完成

严格按 R04 统筹裁决第 2～3 节闭环 `A-M5-06`、`A-M5-07` 与阻断期 `OBS-R03-1` 写入口保护，未扩做通用缓存 revision 架构、多 worker 或排序调参：

1. **A-M5-06（P1）缓存备份阶段中断不误删未备份旧文件（[app/vector_index.py](../../../app/vector_index.py#L590-L707)）**：
   - `commit_candidate_cache`（L617）显式追踪三组不相交文件状态：`backup_moved`（已实际从 `target_dir` 移入 `.backup_*` 的旧文件）、`promoted_files`（已实际从 `.stage_*` 移入 `target_dir` 的新文件）以及尚未触碰的旧文件，并记录 `failure_stage`（`backup_move` / `candidate_promote`）。
   - `_restore_cache_backup`（L590）不再遍历全部 `staged_names` 删除目标文件，改为**仅删除 `promoted_files` 中已实际提升的新文件**，随后将 `backup_moved` 移回 `target_dir`。当在 `backup_move` 阶段任一旧文件（0/1/2/3）移动抛 `OSError` 时，`promoted_files == []`，尚未移动的旧文件零触碰、不丢失，已备份旧文件完整还原；若还原自身再抛 `OSError`，立即调用 `block_cache_writes(...)` 进入持久化写入阻断，保留 `.stage_*` 与 `.backup_*` 恢复材料并抛出 `CacheRollbackError`。
   - 备份候选集同时覆盖 `CACHE_FILE_NAMES` 与 `staged_names` 中可能存在的额外文件名，兼容目标缺件与陈旧 `materials.index` sidecar 清理场景。
2. **A-M5-07（P1）+ OBS-R03-1 所有恢复失败统一隔离、持久化写入阻断与真实核验解除（[app/vector_index.py](../../../app/vector_index.py)、[app/db_manager.py](../../../app/db_manager.py)、[app/server.py](../../../app/server.py)）**：
   - **持久化跨层阻断**：在 `vector_index.py`（L65-167）与 `db_manager.py`（L54-169）分别落盘 `.recovery_blocked.json`（目标缓存目录）与 `<DB_PATH>.recovery_blocked.json` 持久化标记及内存态；进程重启或新建 `VectorIndexManager` / `DbImportLockManager` 实例均无法绕过阻断，生产代码永不调用测试夹具专用 `reset_*_write_block()`。
   - **唯一仲裁与分层失败上报**（`app/server.py` L3060-3530）：`ImportCommitArbiter` 新增终态 `RECOVERY_FAILED = "recovery_failed"`（区别于安全回滚的 `ROLLED_BACK`）。在 `async_process_db_upload_task` 提交门异常分支中，DB 反向交换（`reverse_retained_materials_swap`）、内存索引恢复（`rollback_published_state`）、磁盘缓存恢复（`CacheRollbackError` 或 Step 7 后置清理异常）**任一失败**即记录各层结果 `layer_results`、`recovery_errors` 与 `preserved_materials`，调用 `db_manager.block_db_writes(...)` 与 `vector_index.block_cache_writes(...)`，保留 `materials_old`/`materials_fts_old`、`.stage_*` 与 `.backup_*` 恢复材料，置位 `arbiter.fail_recovery(...)`。任务状态返回 `status="failed"`、`recovery_failed=True`、`recovery_status="recovery_failed_manual_required"`、`write_blocked=True`，且错误文案明确包含 `"恢复失败/需人工处置"`、`"写入阻断"`、失败层与触发原因。
   - **锁与全写入口阻断（含 OBS-R03-1）**：
     - `server.py` 新增 `RecoveryAwareDbImportLockManager`（L3032）：阻断期内 `try_acquire()` 恒返回 `None`；`POST /api/db/upload`（L3546）与 `async_process_db_upload_task`（L3158）入口直接拒绝后续导入并返回 `409` / `recovery_failed`；并发第二请求在回滚期间继续 `409` 且无法释放前序 `owner` 锁。
     - `vector_index.py` 的 `save_cache()`（L356，改用 `get_cache_dir()` 且 `except CacheRollbackError: raise` 不再吞异常）、`build_index()`（L709）、`add_to_index()`（L742）、`check_db_timestamp_and_build()`（L830）与 `write_candidate_cache_to_dir()`（L557）全部在入口执行 `_assert_cache_writable()`；`load_cache()` 同步改用 `get_cache_dir()`。
     - `db_manager.py` 的 `import_materials_from_excel`、`commit_staged_materials_import`、`reparse_materials_db_asymmetric`、`reparse_materials_db_partial` 与 `process_llm_extraction_async` 全部接入 `_assert_db_writable()` / `is_db_write_blocked()`，且 `reparse_*` 不再吞掉 `CacheRollbackError`。
     - `POST /api/refresh_vector`（L1990）与 `POST /api/db/reparse`（L3829）在阻断期均返回 HTTP `409`。
   - **全层一致性核验后解除**：新增 `server.verify_and_clear_recovery_block()`（L3684）与 `POST /api/admin/recovery/verify-clear`（L3817，需 `director` 权限），必须实检 `_db_import_lock` 未占用、无残留 `*_stage`/`*_old` 表、无残留 `.stage_*`/`.backup_*` 目录、`materials`/`materials_fts`/`materials_metadata`/内存索引/磁盘缓存四件套全部一致后，才允许清除持久化阻断标记；任何项不匹配均返回 `409`、`cleared=False` 并继续维持阻断。
   - **跨全量会话导入对齐**：`app/server.py` 统一通过 `importlib.import_module("app.db_manager")` / `importlib.import_module("app.vector_index")` 解析 `sys.modules`，防止 `test_m0_guardrail_regression.py` 清理重载 `app.*` 后导致包属性与 `sys.modules` 漂移。
