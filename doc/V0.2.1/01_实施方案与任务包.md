# V0.2.1 实施方案与任务包

**版本目标**　清单上传完成后，用户能一眼看出系统已经填了多少条、哪些可以集中核对、哪些还需要自己选材。确认和导出进度单独显示。

**状态**　R2，2026-11-22。已按方案评审意见修订，待复审和统筹准入。M0～M3 均未下发。基线为 V0.2.0 RC，提交 `a22fcd4c75c28030915bbdc46c5f0489244bfee0`。本文件是本版本的方案与任务入口。

## 一、工作台显示什么

用历史关键词模式的 1,060 条清单按本方案口径复算，首屏示例如下。

> **系统已自动预填 510 / 1,060 条（48.1%）**  
> 优先核对 34 · 普通候选 205 · 重点核对或补参 344（271 条已预填、73 条待补参） · 无有效匹配或冲突 477  
> **未预填 550 条**　·　**已确认可导出 0 / 1,060 条**

首页显示四档条数。A、B、C、D 合计等于参与匹配的行数。C 档同时拆出“低分已预填”和“安全参数待补”两项。有效规则与组合匹配计入 A 档总数，并标明各自来源。点击任一数字即可查看对应源行。首页默认显示**全单**。切换专业时标明专业及分母。搜索、分页只影响列表。任务完成后才显示正式比例，分母为零时显示“无可匹配物料”。

| 页面位置 | 显示内容 | 何时更新 |
|---|---|---|
| 首屏主指标 | 首次自动预填条数 / 参与匹配的物料行数，百分比保留一位 | 首次上传完成后冻结 |
| 行列表 | 首次已填或未填、分档原因、当前物料、当前确认状态 | 首次结果保留，当前选择及确认随操作更新 |
| 详情及集中核对 | 清单原文、首选物料、匹配评分、关键规格差异、次选及分差 | 用“首次推荐”和“当前选择”标明所看版本 |
| 导出区 | 已确认可导出条数 / 物料行数 | 按当前服务端决定统计，导出时重新校验 |

候选卡显示“匹配评分 96 分”。行上可显示“首次已预填 · 待核对规格”和“当前待确认”。分档与确认状态可组合筛选。原则上优先展示条数，百分比同时给出分母。

## 二、一次自动匹配怎么算

**主指标按工作台实际填写结果计算。** 在最终排序、规则及 BOM 判定后，由服务端生成工作台首轮绑定与预填标记。普通首选、受约束规则的有效绑定，以及集合、数量、单位和逐项约束均通过的 BOM，各按原清单计一行。规则和 BOM 按自身证据核验。仅名称旧规则、失效编码、硬冲突、部分 BOM、单纯的 LLM 建议，以及适用的防爆、提升泵或单位倍率状态未知项，首轮绑定栏留空。可以核对的建议放在候选区，安全关键未知项须先补参再核对。

现有上传响应的 `bindings`、`matched_code` 与规则沙箱输入保留原语义。新工作台通过服务端明确给出的 `initial_match.effective_bindings` 初始化可编辑的当前绑定，并按 `actual_prefilled` 统计。列表、确认按钮、草稿及导出请求统一使用当前工作台绑定。工作台空绑定时显示“待选材”或“待补参”，编码栏采用相同的数据源。新增字段缺失的旧会话走兼容恢复路径，先请求服务端恢复权威决定，再展示当前结果。旧规则提议继续供规则沙箱检测退化。M0 须复验旧规则两组件、数量缩放以及无约束规则检出 17 处退化并判为有害的既有约束。[上传与复核](../../app/server.py) · [规则沙箱](../../app/sandbox_evaluator.py) · [旧规则测试](../../tests/test_auto_binding.py)

分母包括进入匹配的全部有效物料行，含零分、无答案和冲突行；解析器排除的表头、空行不计入。同一源行按服务端文档、工作表和源行标识去重，两行同名物料各算一行。用户重传形成独立上传任务时，统计该任务自己的首次结果。

**复核后的质量用首次采纳率观察**，即“保留首次完整绑定的已复核行 / 已作出保留、改选或拒绝决定的首次预填行”。改选、拒绝计入分母，尚未复核单列。组合物料须编码集合、数量和单位均一致。按逐行确认和集中确认分别报告采纳率、改选率和耗时。

## 三、评分用于安排核对顺序

先识别已经通过权威校验的规则和组合，再按下表处理普通匹配。分档供用户定位待处理行，预填标记取工作台首轮绑定。C 档中的低分项在当前编码有效、无硬冲突且安全条件明确时可以预填。安全条件未知项只展示候选。

| 优先级 | 页面分档 | 判定与操作 |
|---|---|---|
| A（规则或组合） | 规则匹配 / 组合匹配 | 权威规则或完整 BOM 已核验。计入 A 档总数并注明来源，按当前自动接受状态计算可导出进度。该来源跳过集中提交 |
| D | 未匹配 / 冲突 | 无有效候选、首选分数 ≤0、编码失效或发生硬冲突。普通匹配的已知非 1 单位倍率按现行硬冲突处理，空绑定归 D，由用户逐行处理 |
| C | 重点核对 / 待补参 | 排除 D 后，适用安全条件未知或首选评分 <60。低分可用首选可预填，安全关键未知的候选须先补参 |
| A（普通匹配） | 优先核对 | 排除 D/C 后，最终首选评分 ≥75、有效模型输出 ≥0.65，且无已知核心物理参数冲突。列表区分“可逐行勾选”和“仅查看”，资格由第四节规定 |
| B | 普通候选 | 余下可用首选，评分 ≥60。可核对当前推荐或选择其他候选 |

边界值 60.0、75.0、0.65 均按包含处理，服务端以实际模型输出比较。0.65 用于分组；原始评分 90 分可作列表筛选。详情展示影响判断的分差和字段，用户界面不把模型输出换算成正确概率。校准资产缺失、摘要错误或最终排序证据不完整时，普通匹配最高进入 B；同时显示“优先核对评估不可用”。专业、型号、材质、尺寸等适用字段的缺失与冲突分别记录，同义规格由结构化比较处理。

## 四、快照、集中确认与导出

1. **冻结首次结果。** 在 `materials.db` 的首次推荐快照中增加可空 JSON 扩展列 `initial_match_json`。在 `initial_upload`、revision 1 的原事务内写入工作台首轮绑定、预填标记、分档、来源、原因、首选评分、分差、排序证据状态、目录 revision 和统计策略版本。扩展列通过现有迁移入口幂等添加，旧快照的空值表示“未记录”。回放冻结只读库时在临时副本迁移，保留原件。发布回退保留扩展列和已写数据，验证旧读写入口。整单与各专业汇总从同一组源行计算，失败任务只展示任务状态。[上传与复核](../../app/server.py) · [快照](../../app/feedback_contract.py) · [飞轮数据库](../../app/flywheel_db.py)
2. **排序证据。** 在排序器裁成 Top 10 前计算独立分差，记录首选和最强非等价、未阻断对手的轻量摘要。服务端对 Top 10 应用第二遍系列加分时，只要任一评分实际改变，就将旧摘要标为失效。此时普通匹配最高为 B 档。有完整候选池的重匹路径可以重新生成证据，并校验首选和分数与最终结果一致。缺少可靠对手时显示“无可比较候选”，集中提交资格关闭。[匹配](../../app/matcher.py) · [校准资产](../../app/calibration_assets/v019_m2_policy.json)
3. **草稿与重匹。** 单行及批量重算、改选、拒绝、撤销只影响当前结果。恢复时由服务端按用户、文档、工作表和源行读取首轮快照。旧草稿缺乏权威首轮证据时显示“首次统计未记录”。部分缺失时列出已知与缺失条数，整单比例显示“—”。[工作台](../../web/app.js)
4. **集中查看，逐行勾选。** A 档列表默认零勾选，提供“可逐行勾选”和“仅查看”标记。普通 A 档满足实时编码及硬约束检查、单位倍率确认为 1、首选未封顶、最终独立分差 ≥10、当前绑定与首轮绑定一致，且处于待确认状态，才允许逐行勾选。适用的安全关键未知、无可靠对手、排序证据陈旧、BOM、改选、拒绝或过期转单行处理。目录未标注等普通字段缺失须在该行醒目显示字段及缺失方，并展开原文和目录规格对照，由用户明确核对后勾选。若清单明确要求的参数缺少可核验依据，比如指定功率而目录侧无法确认，转单行补证。以 GT-0300 复验这条边界。没有符合条件的行时显示原因，并提供逐行核对入口。
5. **确认按源行隔离。** 已验证谱系的行以 `user_id + document_id + sheet_id + source_row_id` 为确认、拒绝、失效、恢复和导出的作用域。服务端另外验证当前 revision、行及绑定指纹、编码、数量和单位。现有按文件名与内容指纹的凭据只供无已验证谱系的旧会话恢复，已验证源行缺少新凭据时返回待确认。由服务端上传和会话身份确定作用域。伪造或省略已登记源行身份须拒绝。既有凭据无法证明对应单一源行时，引导重新确认。用相同内容的两行和同名重传验证独立确认和独立失效。[绑定与单位校验](../../app/binding_decisions.py)
6. **批量提交与反馈。** 每批有请求标识，每行有绑定源行、当前 revision 与绑定指纹的幂等键。在 `auth.db` 同一事务写入逐行权威决定、幂等回执和待投递反馈。提交前再次核验目录与当前资格，逐行返回成功或失败原因。并发编辑通过 revision 或指纹冲突拒绝。部分成功后重试返回已提交行原回执，并以提交时状态核对其后是否失效。反馈在事务提交后写入 `materials.db`，按稳定事件 ID 去重。反馈失败时保留已确认结果，待投递项继续重试。集中确认事件标记独立来源，禁止写入旧 `binding_feedback.json`，验证规则建议和训练入口的来源隔离。涉及两库的迁移和回退各自验收。
7. **导出。** 使用当前源行的权威凭据，并沿用既有规则及实时校验。无有效凭据的行返回 422。行内容、单位或绑定编辑后应重新确认。导出后重读 XLSX 验证编码与数量。回退时，已验证源行的新版凭据若无法被旧入口识别，按待确认处理。
