## M1-C01 ～ M1-C06 实现摘要与关键口径

### 1. M1-C01：统一聚合 Schema、迁移幂等、失败回滚与历史归档区分口径

- **权威表结构（[flywheel_db.py](../../../app/flywheel_db.py)）**：`flywheel_pattern_aggregates` 统一以 `(source_pattern, suggestion_type, target_value, discipline, source_origin)` 作为 `UNIQUE` 键，字段包含：
  - 历史归档列：`archived_support`、`archived_distinct_users`
  - 实时重算列：`active_support`、`active_distinct_users`、`param_adjust_count`
  - 展示总计与上下文：`total_support = archived_support + active_support`、`dominant_target_code`、`sample_ids_json`、`context_summary_json`、`updated_at`
- **历史归档与实时重算区分**：
  - M0 既有预建库或旧 `pattern_key` 库迁入时统一放入 `archived_support` / `archived_distinct_users`，`source_origin` 保守标记为 `legacy_archive` 或 `legacy_unknown`，绝不伪造归因、不编造专业（保持原 `discipline` 或 `""`），也不并入 `trusted_recompute`。
  - 挖掘器仅对 `source_origin='trusted_recompute'` 行执行重算与增量清除，`legacy_archive`/`legacy_unknown` 归档计数与状态永不被实时任务覆盖或清零。
- **幂等迁移与原子回滚**：`init_flywheel_tables` 在单连接 `BEGIN IMMEDIATE` 中完成 `flywheel_records` 历史列补齐（含超极简表缺失 `created_at` 列兼容）、`flywheel_rule_suggestions` 增补 `source_origin` / `rule_context_json` / `updated_at`（历史 `'通用'` 标记 `legacy_unscoped`，其余历史建议标记 `legacy_pre_m1`）、`flywheel_pattern_aggregates` 建表/平滑重建、视图重建；任一步异常整体 `ROLLBACK`，零半成品残留。

### 2. M1-C02：可信有效集合边界一致性

- **统一过滤口径（[flywheel_db.py](../../../app/flywheel_db.py)）**：扩展 `trusted_flywheel_where_clause` 与视图 `flywheel_effective_records`，强制要求：
  - `trust_level = 'trusted'`、`superseded = 0`、`is_stale_arrival = 0`
  - 非空 `client_event_id`、`payload_digest`、`document_id`、`sheet_id`、`source_row_id`
  - 服务端不可变 `actor_user_id > 0` 与非空 `actor_account_epoch`
  - `EXISTS` 关联真实 `flywheel_documents` 与 `flywheel_source_rows`（拒绝直接向 SQLite 伪造 `trust_level='trusted'` 的孤立脏行）
  - 排除 `session_id = 'default_session'` 与 `user_id = 'legacy_anonymous'`
- **全读者一致性（[feedback_miner.py](../../../app/feedback_miner.py)、[server.py](../../../app/server.py)）**：挖掘增量扫描、全局统计重算、`/api/flywheel/statistics`、`/api/flywheel/export/benchmark`、`/api/flywheel/export/triplets` 均对齐该边界；`distinct_users` 改为服务端不可变 `(actor_user_id, actor_account_epoch)` 聚合去重（不信任可变用户名或旧匿名 ID）。

### 3. M1-C03：`RuleContext` 统一抽象与 `category`/`name` 兼容口径

- **零副作用共享模块（[rule_context.py](../../../app/rule_context.py)）**：新增 `RuleContext`、`RuleScopeResult` 及作用域判定函数，实现严格字段语义分离：

| 上下文字段 | 权威语义 | 别名/兼容规则 | 缺值行为 |
|---|---|---|---|
| `professional` | 专业作用域（`暖通`/`给排水`/`强电`/`医气` 等），匹配 `discipline` 级规则 | 保留已审别称归一：`医用气体` → `医气`；不再从 `category` 推断 | 缺省或为通用值时，不触发 `discipline` 级规则并记诊断 `missing_professional_context` |
| `material_category` | 物料分类/供货分类（如 `甲供材`/`风机盘管`），匹配 `category` 级规则 | 读取顺序 `material_category` → `original_category` → 兼容场景的非专业 `category`；绝不回写 `professional` | 与 `name`/`raw_name` 均缺值时不触发 `category` 级规则，记 `missing_category_or_name_context` |
| `domain` | 领域路由标签 | 由专用路由按需要解析 | 与专业作用域独立判定 |
| `name` / `raw_name` | 物料名称与原始名称 | 支持 `category` 规则基于品名或物料分类匹配 | 无任一目标时跳过并记诊断 |

- **既有接口兼容与全链路传递**：
  - `prepare_query`（[query_preprocessor.py](../../../app/query_preprocessor.py)）保留对现有测试契约 `query_info["category"]` 的返回格式，同时新增并传递独立的 `query_info["material_category"]`；对 `material_block` 使用仅执行动态清洗规则的隔离通道避免正则误伤规格属性。
  - [normalizer.py](../../../app/normalizer.py)、[matcher.py](../../../app/matcher.py)、[preprocessor.py](../../../app/preprocessor.py)、[db_manager.py](../../../app/db_manager.py)、[binding_decisions.py](../../../app/binding_decisions.py)、[server.py](../../../app/server.py) 全链透传 `RuleContext`（如 `/api/match` 与 `/api/rematch` 显式保留 `professional=""` 空字符串语义、区分 `professional` 与 `material_category`）。
  - 解决事务嵌套死锁与缓存污染：在 [llm_rule_engine.py](../../../app/llm_rule_engine.py) 为只读规则查询 `get_active_rules()` 增加不触发建表 `BEGIN IMMEDIATE` 的 `_open_read_conn()`，并在 [feedback_contract.py](../../../app/feedback_contract.py) 的 `persist_upload_document_tree` 将行文本标准化提前至写事务之外执行；[matcher.py](../../../app/matcher.py) 中 `match_item` 不再将降级 `parsed_spec` 写回调用方入参，且 `evaluate_dynamic_exclusions` / `_apply_dynamic_rules` 直接基于当前生效规则做实时分段校验，恢复后立即可用。

### 4. M1-C04：建议键与跨专业隔离

- `flywheel_rule_suggestions` 以 `(suggestion_type, source_pattern, target_value, discipline, source_origin)` 分专业独立收敛与查询；缺专业/通用来源记录仅统计 `skipped_missing_discipline_count`，绝不落入 `"通用"` 桶，也不覆盖历史 `legacy_unscoped`/`legacy_pre_m1` 或跨专业 `accepted`/`rejected`/`rolled_back` 状态。
- `/api/flywheel/suggestions` 新增可选 `discipline` 过滤参数；新增 `GET /api/flywheel/aggregates`（需 `manager` 及以上权限）。M1 严格不自动采纳或自动发布规则。

### 5. M1-C05：单事务边界、并发锁与替代重算

- `FlywheelMiner.run_mining` 使用模块级 `_MINING_LOCK` 与单连接 `BEGIN IMMEDIATE` 包裹全流程：增量未处理扫描 → 建议统计与写入 → 过期/被替代建议调和（降回 `superseded`）→ `PARAM_ADJUST` 聚合与清理 → `is_processed=1` 标记。
- 测试注入 `_tx_hook` 在 4 个关键阶段（首次建议写入后、绑定建议写入后、参数聚合写入后、提交前）抛出异常均触发完整回滚，并发线程竞争严格序列化且累计处理计数与状态零错漏。

### 6. M1-C06：错误显式暴露与脱敏

- 移除 `apply_cleaning_rules` 与 `apply_extraction_rules` 的静默吞错（提取共享正则编译 `_compile_cleaning_regex` 与分段校验 `DynamicRuleInterpreter.validate_rule_stages`）；`clean_text_standard_with_diagnostics` 与 `extract_query_params` 记录 `rule_diagnostics`；`LLMRuleManager.test_rule_execution` 与 `/api/llm-rules/test` 显式返回结构化失败信息；`/api/flywheel/miner/run` 失败通过 executor 显式返回 HTTP 500；日志输出仅保留异常类名与脱敏摘要，不记录密钥/Token/业务敏感原文。
