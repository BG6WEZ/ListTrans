# V020-M3 / R01 审核小结

**V0.2.0 · 审核 AI · 2026-11-22（Asia/Shanghai）· 独立复验完成。结论：退回整改（R02）。**

对象：`V020-M3 / R01` 全系统终验与发布候选（V0.2.0 收口包）。开工 HEAD `e964fb16848de9dece8e729e801b61c7d81dd341` 叠加 M0～M2 放行工作区。本审核不采信开发小结作为结论依据，关键项独立复验。

## 结论依据（为何退回而非通过）

本包验收结果与前三个包不同：**存在明确影响本轮验收的性能缺口，且尚未闭合**。

- 协作协议第 4 节：「任何未闭合 P0/P1 阻断本包及版本终审。P2 只有统筹明确记录原因、后续包、期限/触发条件和防护后才可延期；**影响当前验收的 P2 仍阻断**。」结论三选一，「有阻断问题则退回……均不能写成通过」。
- `V020-M3-PERF-01` 在台账中登记为「**P2，本轮验收项 / 开放 / 待独立审核和统筹裁决**」；统筹尚未作出延期/接受裁决，开发自述「暂未定位超限原因」。性能抽复验是下发明示的必做验收项，实测两次持续超限。
- 历史先例（V018-M1 内存/P50 超预算）是经**统筹放行裁决**记录后才作为已知边界保留。本包的 P2 缺口没有对应统筹裁决，审核不能代为接受，更不能把失败验收项写成通过。

因此判定 **退回整改（R02）**，缺口编号 `A-M3-01`。R02 应做：(1) 定位超限原因——是抽样口径差异（本轮 200 单条/Train-Dev 子集/5 条预热 vs V0.1.7 签认全量 1,220 单条/全量排名后测量）还是真实性能退化；(2) 按签认同口径复测确认是否真实超限；(3) 若确认真实超限且本包无法修复，明确交统筹裁决是否作为 RC 已知边界接受（含原因、后续包、触发条件、防护）。**不改测试断言、不降预算门槛、不改金标。**

`ENV-V017-01`（Linux 镜像待验证）属下发第 17 条预授权的环境受限分支（本机 Docker 两个守护进程端点均不可达），如实标待验证并衔接统筹即可，**不构成退回理由**。
