## 二、标注原理（为何这份真集可以自动标注）

真集的「完成清单」采用造价专业的**人工费父行 + 材料费子行**层级结构：

```
*序号   *费用类型  *清单类型  *材料类型      *清单编码        *清单名称    *特征/规格型号
1.2     人工费     手动录入   （空）         JPS0310040030001  台式洗脸盆   1.名称：台式洗脸盆…   ← 工程清单条目（Query）
1.3     材料费     档案       洗脸盆、洗手盆  2.21.09.0106      台面式洗手盆 陶瓷洗手盆(配感应龙头) ← 造价员选定的标准物料（Answer）
1.4     材料费     档案       水暖及卫浴五金  2.03.07.0112      台盆下水管   φ40*800mm…            ← 同一条目的第 2 个物料
```

因此映射关系为：

- **人工费行** = 一条工程量清单条目，即系统的 Query
- **其下紧随的材料费行** = 造价员人工确认的标准物料，其「清单编码」即 `target_code`
- 遇到 `费用类型 = /` 的分组标题行时**主动断开父子关系**，防止跨组误挂

### 关键设计：Query 文本回溯原始清单，规避答案泄漏

完成清单的人工费行文本被造价员二次加工过（会补充答案线索），例如：

| 来源 | 文本 |
|---|---|
| 原始清单 | `1.名称：台式洗脸盆（非接触感应式）2.材质、规格：台…` |
| 完成清单 | `1.名称：台式洗脸盆（非接触感应式）**（台盆）**2.材质、规格：台…` |

若直接用完成清单文本做 Query，指标会被虚高。因此本测试集：

1. 以 `(项目, 工程清单编码, 清单名称)` 三元组回溯到「原始清单」的对应行，取其原文作为 Query
2. 一名多行时按规格文本相似度择优对齐
3. 回溯结果（去重后 1220 条）：**1156 条精确回溯 / 7 条仅按名称回溯 / 57 条回退用完成清单文本**，`query_source` 字段全程可追溯

已验证：成功配对的条目中 **94.5% 的规格文本与完成清单完全一致**，差异部分仅为造价员的个别字词微调（如「腻子一遍」→「腻子三遍」），不构成答案泄漏。

## 四、标注质检层（重要）

真集本身存在造价员**填表错行**缺陷，构建脚本必须识别并隔离，否则会污染指标。实测案例：

```
R1284  人工费  YQ0308070020085  UPVC球阀       1.名称：UPVC球阀 2.材质:塑料 3.规格：DN20…   单位:个
R1285  材料费  2.28.03.0172     WDZC-BVR 6     WDZC-BVR 6                                  单位:m   ← 明显错行，配到了电线
```

质检规则（`qc_check`）：

1. **名称零交集**：Query 名称与目标物料名称/材料类型的中文字符 Jaccard = 0，且规格文本中也不含目标名称片段/英文型号 → 判可疑
2. **低交集 + 单位大类冲突**：名称交集 < 0.15，且计量单位跨大类（长度 m ↔ 计件 个/台/套 ↔ 面积 ㎡ ↔ 重量 kg）→ 判可疑

命中 12 条，标记 `qc_suspect=true`，主指标默认剔除但保留在文件中可追溯。

## 六、评测指标定义

| 指标 | 定义 | 建议目标 |
|---|---|---|
| **Hit@1** | Top-1 候选即正确答案的比例 | ≥ 85% |
| **Recall@3** | 前 3 个候选包含正确答案的比例 | ≥ 90% |
| **Recall@5** | 前 5 个候选包含正确答案的比例 | ≥ 93% |
| **Recall@10** | 前 10 个候选包含正确答案的比例 | — |
| **MRR** | 平均倒数排名，未命中记 0 | ≥ 0.88 |
| **miss@10** | Top-10 完全未命中的比例 | 用于区分「召回漏」与「排序错」 |

`miss@10` 是关键归因指标：
- `miss@10` 高 → 问题在**召回层**（FTS5 分词、型号前缀、向量语义），优化方向是路线图第四步
- `miss@10` 低但 `Hit@1` 低 → 问题在**打分排序层**，优化方向是路线图第三步（参数抽取与硬门禁）

> 注：`match_item` 的 `top_candidates` 固定只返回 Top 10（[matcher.py L1243](file:///c:/Users/wangd/project/ListTrans/app/matcher.py#L1243)），因此本评测最深只能观测到 Rank 10。

## 七、评测输入与生产流程的一致性（关键）

评测若不复刻生产的调用链，指标毫无意义。本脚本已严格对齐 [batch_match_rows](file:///c:/Users/wangd/project/ListTrans/app/server.py#L908-L1010)：

| 环节 | 生产流程 | 评测脚本 |
|---|---|---|
| 文本清洗 | `extract_query_params(raw_name, raw_spec, prof)` | 同 |
| 实际入参 name | `parsed_info["name"] or raw_name` | 同 |
| 实际入参 spec | `parsed_info["spec"] or raw_spec` | 同 |
| `category` 取值 | 甲供材品类 → professional → name | 同（故测试集必须保留 `supply_category` 字段） |
| 向量化 | 分块批量 `encode_queries`，结果传入 `match_item` 第 2 参 | 同 |
| 打分 | `match_item(query_info, q_vector)` | 同 |

首版评测脚本曾直接把原始 name/spec 丢给 `match_item`（未走 `extract_query_params`、未传向量），实测 Hit@1 仅 6%，属评测方式失真而非系统真实水平。对齐后为 22.31%。

### 8.3 基线的核心结论

**当前 Hit@1 仅 22.31%，距 85% 目标有 63 个百分点的差距，且 `miss@10` 高达 48.92%。**

`miss@10` = 48.92% 意味着近一半的错配是「正确答案根本没进 Top 10」，**主要矛盾在召回层，而非排序层**。短板集中在医用气体（68.4%）、自控（64.7%）、弱电（60.9%）三个专业。

这直接修正了路线图的优先级判断：单纯打磨第三步（参数抽取 + 硬门禁）最多只能改善已进入 Top 10 的那 51.08%，即便排序做到完美，Hit@1 天花板也只有 51%。**召回层扩容与召回质量（路线图第四步）必须与第三步并行推进，不宜后置到 P2。**

反过来看，Recall@10 为 51.08% 而 Hit@1 仅 22.31%，说明进入 Top 10 的样本里有超过一半没能排到第 1 位，排序层同样有大量可挖空间。两条战线都要打。

### 8.4 典型错配模式（已定位，可直接指导第三步）

**模式 A：外径 ↔ 公称直径量纲混淆，导致假满分**

| Query | 正确答案 | 系统 Top-1 | 得分 |
|---|---|---|---|
| 不锈钢球阀 规格 D27 焊接 | `2.19.71.0007` | `2.19.71.0255` 不锈钢球阀 **DN25** | 100.0 |
| 不锈钢球阀 规格 D34 焊接 | `2.19.71.0009` | `2.19.71.0255` 不锈钢球阀 **DN25** | 100.0 |
| 不锈钢球阀 规格 D42 焊接 | `2.19.71.0011` | `2.19.71.0255` 不锈钢球阀 **DN25** | 100.0 |
| UPVC管 规格 De32 粘接 | `2.17.25.0083` | `2.17.25.0176` UPVC SCH40 **D60.3** | 100.0 |

Query 用外径（`D27` / `De32`），物料库用公称直径（`DN25`），系统未区分量纲即判「规格完全一致」给满分 100。三条不同口径的球阀全部撞到同一个 DN25，且分数一致到无法排序。**这是一票否决门禁的明确缺口。**

**模式 B：电缆型号阻燃等级/系列名错配**

| Query | 正确答案 | 系统 Top-1 |
|---|---|---|
| 控制线 WDZ-RYYSP-2*0.75mm² | `2.28.03.3850` WDZB-RYYSP 2*0.75 | `2.29.06.0015` SC线管 50 |
| 配线 WDZ-RYY-2*1.0 | `2.28.03.3112` WDZB-RYY 2*1 | `2.28.43.0272` WDUZB-**KYJY** 2x1.0 |

`WDZ-` 与 `WDZB-` 前缀差一个字母即判为不同系列，而 `RYY` 与 `KYJY` 属完全不同的线型却被判为高分（66.7）。**需补电缆型号的结构化解析（阻燃等级 + 线型 + 芯数 × 截面积）。**

**模式 C：名称同义但库内命名体系不同**

如 `三气报警面板` → 库内为「报警装置」、`医用设备带` → 库内为「医气设备带」、`一氧化碳浓度仪` → 库内为「露点检测仪」。属别名库缺失，对应路线图第二步与第三步的同义词补充。

## 九、发现的系统级缺陷（需修复）

### 缺陷 1：向量索引缓存维度失配后静默降级（P0）

首次评测时报：

```
Numpy embeddings dimension mismatch: got shape (47750, 384), expected (*, 512). Need rebuild.
```

Embedding 模型已升级为 `bge-small-zh-v1.5`（512 维），但磁盘缓存仍是旧 `MiniLM` 的 384 维产物。[load_cache](file:///c:/Users/wangd/project/ListTrans/app/vector_index.py#L163-L175) 返回 `False` 后，**系统并未自动重建，也没有任何告警，而是让向量召回通道静默失效**——三通道混合召回悄悄降级为「型号前缀 + FTS5」两通道。

这是本次建立基线过程中最危险的发现：**系统可以在向量召回完全失效的状态下"正常"对外服务，界面上没有任何异常提示**，长尾语义匹配能力归零而无人知晓。若非评测脚本打印了这行日志，该问题不会被发现。

评测脚本已加入 `load_cache()` 失败即自动重建的保护（本机重建 47750 条耗时约 517 秒）。**建议在 [server.py](file:///c:/Users/wangd/project/ListTrans/app/server.py) 启动流程中做同样处理，至少要在管理端显式告警。**

### 缺陷 2：真集源数据存在填表错行（数据侧，已隔离）

见第四节，共 12 条，已由质检层自动标记隔离，不影响指标。建议反馈给造价团队修正源表。

## 十、内存与性能约束（16G 机器）

本机 16G 内存，评测曾因内存不足导致进程崩溃。已做三项优化：

1. **分块流式评测**：默认 `--chunk-size 200`，块内预处理 + 向量化 + 匹配完成后立即 `del` 并 `gc.collect()`，不再一次性持有 1000+ 条的向量与候选对象
2. **限制 BLAS/OMP 线程数为 2**：`47750 × 512` 的向量矩阵做 einsum 时，多线程会各自开辟私有缓冲区，是内存峰值的主要来源
3. **明细文件流式写盘**：逐条 `json.dump` 追加，避免一次性构造上兆字符串

已验证：`--chunk-size 100` 全量跑完 1067 条无崩溃，且指标与 `--chunk-size 200` **完全一致**（22.31 / 35.61 / 42.92 / 0.307），门禁比对全部 `+0.00`，可复现性得到确认。

内存紧张时可进一步降到 `--chunk-size 50`。构建脚本 [build_golden_set.py](file:///c:/Users/wangd/project/ListTrans/tests/build_golden_set.py) 也已改为逐 Sheet 释放 DataFrame。

## 十一、使用方式


新增项目需在脚本内补两处配置：`PROJECT_OF`（文件 → 项目号）与 `PROF_MAP`（Sheet 名 → 专业标签），Sheet 名未登记时会按工程编码字母前缀（ZS/TJ/QD/RD/JPS/NT/YQ/SB）兜底判定。

### 11.2 执行评测

```bash

```
