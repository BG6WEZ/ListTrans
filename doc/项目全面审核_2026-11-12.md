# ListTrans 项目功能、代码与匹配质量审核

审核日期：2026-11-12。代码基线：`4cbbbe5bd6e1bee21ad908ed1f631a919920ea8f`，以及工作区现有文件。本文是独立审核，不把历史开发、验收文档中的“100%闭环”视为已经验证的事实。

## 1. 结论与审核边界

项目已经形成可用的人机协同物料匹配工作台：Excel 清单导入、多专业识别、参数提取、关键词与向量混合召回、领域规则打分、人工调整与多物料绑定、草稿和命名进度、标准报表导出、账号权限、动态规则和反馈飞轮均有实际代码实现。

但是，目前不能据此认定项目已经达到高准确率、可靠自动绑定或完整反馈闭环。最重要的问题集中在：**生产与评测入口不一致、低可信候选进入绑定与导出、专业和属性提取误判、规则审批与硬约束可被绕过、飞轮流水失真及上线门禁没有真正闭合。**

本次完成：

- 梳理 `app/` 的服务、匹配、数据库、清洗、向量、权限、导出、规则和飞轮模块，以及前端核心状态流转、测试与容器配置。
- 对 `app/`、`tests/` 共 40 个 Python 文件进行不执行模块的语法编译检查，无语法错误。
- 运行现有两组清洗与提取测试，共 **31 项通过**。
- 使用生产函数源码进行定向反例验证；数据库以只读方式核验，规则写入与聚合 SQL 在内存库验证。
- 提供复核脚本 `doc/audits/2026-11-12/audit_20261112.py` 和结果 `doc/audits/2026-11-12/audit_20261112_results.json`（原在scratch，目录整理后迁入此处；重跑另写rerun结果，不覆盖原始证据）。脚本为适应缺少 pandas/FastAPI 的本机环境，使用 AST 载入只读数据库代码与指定服务函数，跳过模块初始化；批量绑定反例使用受控候选。它验证分支行为，不代表完整生产链路或匹配率实测。

限制：当前 Python 环境缺少 FastAPI、pandas、pytest、sentence-transformers 等主要依赖，Docker 引擎未运行，隔离环境安装依赖的网络访问未成功。因此**未完成完整 HTTP 端到端测试、向量模型全量黄金集复测、真实并发压测和浏览器交互验收**。文中历史匹配指标明确标为仓库留存记录，不冒充本次实测。未修改业务源代码，也未部署远端服务。

## 2. 实际业务逻辑

### 2.1 从上传到导出

1. 用户登录：JWT 携带用户 ID、账号、角色；每次鉴权再查数据库，验证账号仍存在、仍启用，并根据最新角色授权。
2. 上传 Excel：后台任务扫描工作表，用表名推断专业，在前十行寻找表头，提取名称、规格、单位、工程量、损耗、品类和品牌；过滤空行、汇总、标题等非物料内容。
3. Query 结构化：拆分名称与规格、去除施工噪声、解析编号与键值块，路由到领域，提取型号、数值、材质、尺寸、功能标志等，并做单位与别名归一。
4. 候选召回：型号检索、FTS 名称检索、抽取名称检索、中文名称补充、暖通专项分支，以及向量 Top-50 合并去重。
5. 候选打分：专业/品牌/单位前置检查；型号、名称、品类、属性与语义加权；Schema 冲突、线缆/管道/电气/暖通规则调整；动态规则调整；最后处理饱和分与并列候选。
6. 自动判断：首选分数 ≥75 被标记 `is_exact`；批次已确认系列可给其他候选加分；已有名称绑定规则可以覆盖模型结果。
7. 工作台复核：展示候选、编辑参数与数量、重新匹配、人工多物料绑定，保存草稿或命名会话。
8. 导出：按专业分组，原清单行与绑定材料行分别写入 Excel；匹配价格从服务器固定模板读取，并非用户上传文件中的历史报价。

### 2.2 数据与规则

- `materials.db`：物料、FTS、LLM 缓存、LLM 节点与规则、飞轮记录和快照。
- `auth.db`：用户、登录尝试、工作会话，以及审计和统计相关表。
- `config/`：同义词、材质、单位、领域 Schema、公差、权重、加减分、自动绑定规则。
- `vector_cache/`：物料文本向量、编码映射、缓存元数据。
- 反馈同时存在旧 JSON 文件路径与新 SQLite 飞轮路径，两套治理方式并存。
- LLM 实际用于规则生成、物料库缺失参数补充等。`check_match_by_llm()` 虽然存在，但生产匹配调用链没有调用；不能把它描述为当前每条清单都经历了大模型复判。

### 2.3 值得保留的设计

- 领域 Schema、数值公差、业务硬约束，比单纯名称相似度更适合工程物料。
- 混合召回和批量向量化方向合理；物料编码去重后再做细粒度打分，流程清晰。
- 匹配主函数拆为上下文和分阶段函数，有利于进一步写故障定位与回归用例。
- 有参数化 SQL、bcrypt、角色鉴权、账号状态复核、HTML 转义、上传清单流式限额等实质防护。
- 向量重建已有局部构建后引用切换；配置有原子写入与快照补偿的基础。
- 已明确单进程部署约束，并记录了行级线程负提速的实测结果。当前规模不需要仅为架构形式就迁移微服务或更换数据库。

## 4. 优先解决的问题

P1：应优先修复，可能污染业务结果、全局规则或关键反馈。P2：条件性错误、稳定性缺陷或明显治理不足。以下“已复现”均指本报告复核脚本中的受控定向验证，不意味着线上已经发生。

### F01 / P1：生产清洗结果没有完整进入匹配，评测入口与生产入口不同

证据：`app/server.py:1162`、`tests/eval_golden_set.py:75`、`app/query_preprocessor.py:818`附近返回结构。

提取器返回的是 `attrs.名称`、`clean_text`，生产批量函数读取 `parsed_info.name`、`parsed_info.spec`，通常不存在，便回退原始名称和规格；评测器却正确读取 `attrs.名称` 和 `clean_text`。生产虽然仍传了结构化 attrs，但召回名称、向量文本、文本相似度与评测不一致，施工噪声仍进入这些步骤。

已复现：“普通阀门 + 名称：卫生级球阀 + 工作内容”被提取为卫生级球阀与干净规格，批量匹配实际收到的仍是普通阀门和含施工内容的原文。

改法：只保留一个 `prepare_query()` 契约，批量、单条、重算、黄金集及沙箱全部调用；原始文本单独保留作追溯。评测调用实际生产匹配管线，而非手工复制另一套预处理。

### F02 / P1：0分或被硬阻断的候选仍能被预绑定并导出

证据：`app/server.py:1326`、`app/report_generator.py:188`、`web/app.js:2230`附近。

`match_item()` 会返回低分甚至0分候选；批量函数只要有第一候选就生成 `bindings`，不检查是否有效、是否冲突、是否确认。导出器优先写 `bindings`，前后端没有强制人工确认门禁。

已复现：受控0分候选在 `is_exact=false`、`matched_code=''` 时仍进入绑定列表。由此可沿导出代码确认该绑定会写入报表。

改法：候选、自动接受、人工确认分开建模；被排除项不得成为绑定；未确认或未通过自动接受标准的行导出时应被明确提示并按业务策略处理。不能把“有推荐结果”计为“匹配完成”。

### F03 / P1：自动绑定只看名称，忽略规格、专业、品牌与有效状态

证据：`app/server.py:1147`、`app/server.py:1266`、`app/server.py:1294`。

规则键仅为原始名称。相同“普通阀门”的DN15、DN100均命中同一规则，并且直接 `is_exact=true`；绑定还保存了历史物料文本，没有重新检查当前库是否存在、已停用或换码。旧规则确认/删除接口只要求 employee 权限，会影响所有用户。

已复现：DN100查询被名称规则绑定到DN15编码。当前本地规则文件为空，说明是**可触发缺陷**，不声称现有本地业务结果已经被这条规则污染。

改法：用专业、物料族、关键规格、品牌约束和规则版本组成适用条件；命中后仍过硬约束并按编码回表；全局规则发布走统一审批。跨规格配套应使用明确公式与约束，不能只记一个名称。

### F04 / P1：普通员工可以绕过规则审批，修改或启用全局规则

证据：`app/rule_api.py:63`、`:100`、`:108`；`app/llm_rule_engine.py:697`、`:845`、`:882`。

更新和toggle接口允许employee；manager方法没有作者、状态、发布角色检查。toggle把任何非approved状态改成approved；普通员工可直接启用草稿。update可直接改已批准规则并清缓存，无须重新审核；保存草稿接口传现有rule_id也可覆盖别人规则。

已复现：内存库中另一作者的draft规则，被employee身份调用toggle后变为approved。

改法：服务层落实状态机和授权：作者编辑草稿、审批者审批、发布者启停；已发布内容修改产生新版本并重新审核。不能只依靠前端按钮隐藏。

### F05 / P1：反馈会话标识错误，跨清单、跨用户记录会相互置为过期

证据：`web/app.js:1713`、`:2968`；`app/server.py:1609`附近的superseded更新。

前端实际变量是 `activeSessionId`，上报却读未定义的 `currentSessionId`，从而落到 `default_session`。后端只按session_id和row_idx覆盖早期记录，没有user_id条件。不同用户或不同文件的“第1行”会被当成同一业务行。

同时，上报使用 `item.discipline`、`item.extracted_params`，主链路数据是 `professional`、`parsed_spec`，导致专业和提取上下文丢失；算法和配置版本是固定常量，不能可靠追溯。

改法：上传时生成稳定的业务任务ID，和保存进度ID分开；所有流水带不可变user_id、task_id、sheet_id、source_row_id及真实版本；覆盖仅发生于同一个业务对象。

### F06 / P1：飞轮参数调整聚合的SQL与表结构不一致

证据：`app/feedback_miner.py:295`、`app/flywheel_db.py:110`附近。

聚合代码往 `flywheel_pattern_aggregates` 写 `pattern_key`、discipline、total_count等字段，但建表定义是source_pattern、suggestion_type、target_value、archived_support等。出现至少两条同名称PARAM_ADJUST记录时，就会进入错误分支，当前挖掘事务失败。

已复现：按生产DDL创建内存库、插入两条参数调整，得到 `table flywheel_pattern_aggregates has no column named pattern_key`。

改法：统一迁移和SQL契约，加含参数调整记录的真实挖掘回归。定时任务失败须可见，不应只在日志出现。

### F07 / P1：沙箱通过没有被服务端强制要求，绑定规则评测又没有执行绑定

证据：`app/server.py:1702`、`:1758`；`app/flywheel_sandbox.py:85`、`:116`；`tests/eval_golden_set.py:115`附近。

accept接口没有检查通过的评测任务及其规则内容哈希，快照却把 `targeted_eval_passed` 固定写1。管理员可以未评测就采纳，或者评测后编辑成另一份内容再采纳。

绑定建议虽然被注入auto_binding_rules.json，评测器只调用match_item，不调用使用该文件的batch_match_rows。因此绑定规则实际上没有参与比较，结果不变也可能通过“稳态”门禁。

沙箱又只测source_pattern关键词子集，无法保护全局别名对其他物料的误替换；子进程没有timeout，且returncode未作为成功前提。两个进程还会覆盖同一golden_last_run路径，结果归档存在串扰风险。

改法：评测覆盖真实管线、定向集和全局保护集；将建议内容哈希、数据/模型/配置版本与结果绑定；accept必须校验；人工编辑强制重测；分别写独立结果路径并限制运行时长。

### F08 / P1：按当前Docker构建，沙箱依赖的评测程序不会进入镜像

证据：`.dockerignore:27`排除tests，`Dockerfile`只COPY过滤后的构建上下文，compose未挂载tests；沙箱硬编码运行tests/eval_golden_set.py。doc也被排除，固定模板与人员清单等依赖同样需要单独解决。

这不是“线上已经复现失败”的声明，而是当前构建配置与调用路径的确定性矛盾。

改法：将运行时评测器移到正式应用模块，显式打包经授权的评测数据；构建测试镜像并执行最小沙箱冒烟。运行资产、开发文档与测试代码应有清晰打包清单。

### F09 / P1：否定表达被识别成肯定，专业别名被当作冲突

证据：`app/query_preprocessor.py:545`、`:560`；`app/matcher.py:242`、`:379`。

- “非防爆”先命中包含“防爆”的if，后面的elif永远不起作用；“不带冷凝水提升泵”也命中“提升泵”。两者均已复现。
- 传入“医用气体”，候选推断返回“医气”，字符串比较会直接0分阻断。已用氧气终端反例复现。自控/弱电、洁净装饰/装饰等也需要统一映射，而非直接拿展示名称做硬约束。
- 当前专业判断还把规格中的风机、开关等单个关键词当作强证据，复合设备可能被内部配件文字误分类。

改法：否定优先且支持“不带/非/无/不含”；未说明采用unknown，不能自动推断为否。专业用统一枚举与兼容矩阵，区分弱提示与强证据。

### F10 / P1：后续动态加分可突破硬约束上限，排除规则只是减分

证据：`app/matcher.py:1003`、`:1554`及score_candidate调用顺序。

Schema hard gate先封顶，后续动态规则仍可加到1.0；DynamicRuleInterpreter返回excluded后，调用方也只是减0.60，没有把候选从可选集删除。

已复现：管径冲突先封顶0.3，再经动态关键词+100变为1.0。该反例验证规则顺序错误，不声称当前已批准规则中存在这条+100配置。

改法：把blocked与max_score作为不可逆约束保存到上下文，最后统一落实；硬排除在打分前剔除，所有学习分与动态加分必须服从约束。

### F11 / P1：未跟踪部署脚本保存了明文远程登录凭据

证据：`scripts/deploy_cloud.py:8`、`scripts/deploy_to_cloud_safe.py:9`。本文不复制凭据内容，也未连接或操作远端。

改法：迁移到密钥认证或安全凭据注入，并轮换现有明文凭据；避免纳入提交、日志或发布包。另需将.env和运行数据库从Docker构建上下文排除，当前.dockerignore未排除.env，COPY会把它写进镜像层，compose的env_file不能消除这个副本。

## 6. 怎样提高匹配率

### 6.1 先定义真正要提高的指标

不要只提高“有绑定的比例”。建议同时跟踪：

| 指标 | 计算与用途 |
|---|---|
| 可匹配覆盖率 | 当前有效物料库里存在可接受答案的查询比例；换码要用映射表识别 |
| Candidate Recall@100/200 | 排序前候选集合包含正确答案的比例；定位召回漏失 |
| Hit@1、Hit@3、MRR | 衡量排序，区分“找到但排错” |
| 自动接受准确率 / 自动接受覆盖率 | 已自动接受里有多少正确，以及多少输入能自动处理；两者必须一起看 |
| 错误绑定率、正确拒绝率 | 防止把不存在物料或关键规格冲突的查询硬配出去 |
| 一对多集合准确率 | 既检查材料集合，也检查各项数量比例；命中其中一项不算完成 |
| 人工修改率、复核耗时 | 判断建议是否真正减少工作量 |
| 关键字段正确率 | 型号、材质牌号、尺寸、口径、功率、控制/防爆等分开统计 |

当前评测只输出排序后Top10，miss@10既可能是召回没找到，也可能是排序挤出了前10，不能据此直接判定“召回漏”。需要记录召回原始集合、渠道、候选规模及真实目标经过哪一步被挡掉。

### 6.2 第一优先级：修输入、字典与标准库

1. 统一生产/评测预处理契约，保留原文、清洗文本、规范名称、域、类型化attrs和抽取证据。这比先换更大模型更直接。
2. 规范专业和物料族枚举；品牌、材质牌号、型号、单位做统一归一。型号区分真实产品型号和项目设备位号，AP-1、AHU-J等不能一律按产品型号处理。
3. 修否定、范围、不等式、数值类型、单位倍率及DN/外径混淆。每个关键属性保存value、unit、operator、source_span、confidence、unknown状态。
4. 用字段白名单避免把施工描述、编号标题或整句话当作核心属性参与打分；以字段抽取正确率而非“JSON不为空”验收。
5. 给当前库建立停用状态、换码关系、等价物料组和生效时间；157组同名同规格需检查品牌和单位后再决定是否合并，不应直接删除。
6. 核对338条失配金标：换码则映射、停用则调整可接受答案、确实无替代则转为无匹配测试；保留旧快照基准，避免通过删难样本抬高指标。

### 6.3 第二优先级：改召回

- 精确编码直达、规范型号、标准名称、别名、字符级关键词、结构化规格过滤与向量分别召回，记录每路贡献。原始清单编码须先区分项目编码和标准物料编码。
- 先按物料族与可信专业限制候选，再用材质、口径、型号、尺寸等组合检索；信息不确定时走多域召回，避免一次误路由就彻底失去答案。
- 评测向量Top50、100、200的候选覆盖率与耗时，按领域确定预算。FTS长串AND查询过严时，应加入规范名称与关键参数的拆分查询，而不是只取名称前四字兜底。
- 记录FTS/BM25与向量各自排名，再尝试RRF融合，减少不同量纲得分直接相加带来的偏置。RRF有公开原始研究，可作为实验候选，而非未经评测的必胜替换：[SIGIR 2009论文](https://doi.org/10.1145/1571941.1572114)。
- 索引增加规范名称、领域、核心参数与有效别名；长规格按关键字段构造文本，降低施工文字和模型截断的干扰。查询与物料的编码文本应采用相同字段规范。

### 6.4 第三优先级：改排序与接受策略

- 将硬排除、上限约束、相似度排序分离。材质牌号、线芯与截面、防爆、额定参数等关键冲突必须在最后也得到保障。
- 按物料族校准权重，避免型号、名称、多个同义参数及一系列boost重复计分导致大量候选饱和到100。
- 尝试“召回100—硬约束—Cross-Encoder重排前20/50—参数一致性检查”；CPU环境先测延迟再定预算。Sentence Transformers官方推荐检索后对小候选集重排，但本项目收益必须以自身留出集验证：[官方Retrieve & Re-Rank](https://www.sbert.net/examples/sentence_transformer/applications/retrieve_rerank/README.html)。
- BGE余弦相似度和手写业务分都不是正确概率。BGE模型卡明确提醒阈值依赖数据与任务；不要把语义分或75分直接解释成“75%可信”：[BGE模型卡](https://huggingface.co/BAAI/bge-small-zh-v1.5)。
- 自动接受至少同时考虑关键属性无冲突、Must完整性、Top1/Top2差距、域内校准概率和歧义状态。阈值需要在验证集上按错误成本确定。
- 允许输出“无适配标准物料”“需要补充参数”“多个等价编码待选”。减少错误自动绑定通常比提高表面覆盖率更有业务价值。

### 6.5 第四优先级：让反馈真正改善模型

- 先修会话、身份、行对象、字段与版本记录；区分确认、替换、候选选择、多物料、参数调整和无匹配，保存初始推荐与最终选择，不用被修改后的候选冒充初始结果。
- 挖掘按专业、物料族、规范名称与关键规格聚合；多个项目和不同用户的独立支持比重复点击次数更可信。
- 样本由复核人员确认后进入训练集；按项目和时间留出验证/测试集，避免同项目相似清单泄漏。当前黄金集只有两个项目，应扩大项目与时间覆盖。
- 对错配构建hard negatives，例如同名称不同DN、同型号不同截面、304/316L、带泵/不带泵。先训练/验证排序器，再考虑微调向量模型。
- LLM先用于低置信度参数提取和候选解释，输出必须限定现有编码并通过硬约束；无须给所有行增加一次昂贵调用。当前未接入生产的LLM复判如要启用，应另设超时、预算、缓存版本和“无答案”分支。
- 一对多需要配套BOM或带参数约束的模板，显式计算数量和单位，单一目标排序模型不能完整解决。

## 7. 建议实施顺序与验收

以下是实施顺序，不是未经测量的工期承诺或准确率保证。

| 顺序 | 工作包 | 可验收结果 |
|---|---|---|
| 1 | 修F01—F04、F09—F10，隔离明文凭据 | DN100不会被DN15名称规则接受；0分候选不会进入正式导出；普通员工不能发布规则；否定/专业别名用例通过 |
| 2 | 修F05—F08、F27，统一评测与生产管线 | 两个用户同一行号互不覆盖；PARAM_ADJUST挖掘不报错；未通过/内容变更的建议不能采纳；正式镜像可运行沙箱 |
| 3 | 库快照、换码与金标治理、错误归因 | 每次评测记录commit、库revision、配置哈希和模型版本；338条逐条有明确分类；报告目标在库/不在库两套结果 |
| 4 | 结构化召回、TopK预算与融合实验 | 同一留出集比较candidate recall、Hit@1、自动接受准确率/覆盖率与P95，不只比较综合分 |
| 5 | 重排、领域权重与反馈训练 | 新模型通过域内/跨域/关键冲突保护集；保留可回滚版本，人工纠正率有可重复下降 |

必须补齐的回归场景：同名不同规格、否定/未知、专业别名、同牌不同材质、线缆复合芯数、DN/De、数量单位转换、被排除项后续加分、无答案、Top1近并列、一对多数量、重新绑定后导出、库更新后缓存失效、跨用户流水、直接越权API、生产镜像沙箱启动。

我的项目意见是：**保留现有领域规则与人工复核的基础，先把输入契约、正确绑定和可重复评测做好，再按召回漏失与排序错误的占比选择算法。** 当前最有把握的收益来自修复已经证实的链路错误与标准库/金标失配；RRF、重排或微调属于值得开展的对照实验，本文不承诺未经测试的提升百分点。
